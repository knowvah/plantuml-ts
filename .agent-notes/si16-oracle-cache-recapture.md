# SI16 — re-capturing the committed oracle caches

## Observation: `oracle-render.sh`'s out-dir must be ABSOLUTE

- **Context**: Re-capturing `test-results/dot-cache/{usecase,state,class}` by
  running `scripts/oracle-render.sh <fixture-dir> <fixture-dir>/in.puml` for
  each fixture, with `<fixture-dir>` given as a repo-relative path.
- **Finding**: PlantUML resolves a relative `-o` against the **input file's**
  directory, not the cwd. Every render therefore landed in
  `<fixture-dir>/test-results/dot-cache/<type>/<slug>/in.svg` and the real
  cache was left untouched. 538 nested directories, and `git status` showed
  only untracked dirs — no `in.svg` modified. The run reported success
  throughout: the wrapper's exit code is 0 whether or not the file landed
  where you meant.
- **Impact**: A re-capture that appears to work and changes nothing is the
  same failure mode SI16 exists to fix — a measurement that is an artifact.
  Pass `"$(cd "$dir" && pwd)"`. Verify with one fixture and a hash before
  launching the corpus.
- **Confidence**: High — reproduced, then fixed and re-verified by md5 on
  `usecase/baxodi-80-doto381`.

## Observation: the jar's SVG output does not depend on the input filename

- **Context**: Wanted one JVM start for the whole freshness guard instead of
  one per type; that needs each sentinel copied in under a distinct basename.
- **Finding**: Rendering `object/beruju-17-jigi548`'s `in.puml` as
  `object-sentinel.puml` produces a file byte-identical to the cached
  `in.svg`.
- **Impact**: Lets a multi-fixture guard (or any batch capture) share a single
  `oracle-render.sh` invocation. Does NOT extend to the `.dot` dumps, which
  are always named `svek-N.dot` and would collide across fixtures in a shared
  out-dir — batch only when you want the SVG.
- **Confidence**: High — byte-compared.

## Observation: the `dot` type's cache tracks the HOST graphviz version

- **Context**: Checking every cached type for staleness before widening the
  freshness guard.
- **Finding**: `dot/bemepi-16-kuzo249`'s cached and freshly rendered SVGs are
  the same length and differ on exactly one line — `<!-- Generated by graphviz
  version 15.1.0 (20260618.0150)` vs `15.1.1 (20260805.0921)`. `@startdot` is
  a passthrough: the jar shells out to the host graphviz binary.
- **Impact**: A byte-equality freshness guard on `dot` reports the local
  graphviz version, not cache staleness. Excluded from the guard for that
  reason (the cache also gates nothing — the dot ratchet reads
  `oracle/goldens/svg-dot/`). Any future capture of that type stamps the
  capturing machine's graphviz version into the repo.
- **Confidence**: High — diffed.

## Observation: `svg-parity-survey.ts`'s default timeout no longer survives this tree

- **Context**: Regenerating `parity-{class,state}.json` / `parity.json` after
  the re-capture, at the concurrency the class ratchet's own header documents.
- **Finding**: The run wrote `parity-state.json` with `{timeout: 270,
  diverged: 1}` of 271 — against a committed file holding `{diverged: 212,
  conformant: 52, structural-match: 7}`. `RENDER_TIMEOUT_MS` defaults to
  10s (`scripts/svg-parity-survey.ts:57`) and each fixture renders in a
  spawned `jiti` subprocess that re-transpiles `src` every time: a single
  `--render-one` measures **11.8s**. Discriminating experiment, on the
  3-fixture `hcl` type: **2 timeouts of 3 at the default, 0 of 3 at
  `SVG_PARITY_TIMEOUT_MS=60000`**, with real verdicts both times for the one
  that completed.
- **Impact**: Any survey run at the default silently converts measurements
  into `timeout` verdicts and writes them over good data. Independent of the
  cache — the render path never reads `in.svg` for timing. Raise the env var
  before any regeneration; tracked as SI19. Revert a bad run rather than
  keeping it: a `timeout` row is not a finding.
- **Confidence**: High — reproduced both directions on a bounded fixture set.

## Observation: three state fixtures are error diagrams

- **Context**: The first capture run reported non-zero exit for
  `state/{fugedo-34-fice721,cagego-53-vemo516,xacona-99-peze211}`.
- **Finding**: The jar prints `Some diagram description contains errors` and
  exits non-zero, but still writes an `in.svg` — the rendered error image.
  These are legitimately-captured fixtures, not capture failures.
- **Impact**: A capture script that treats a non-zero exit as "skip this
  fixture" would silently leave those three stale. Log the exit code, but
  judge freshness by comparing the file.
- **Confidence**: High — reproduced individually.
