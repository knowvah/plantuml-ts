## Observation: dot-engine's edge-label placement is invariant under node declaration order

- **Context**: SI31 T6 (G20a). Reordered `acc.nodes` in both composite passes
  to the jar's real creation order to close `kejabo-83-vinu490` scope-2 width
  idx2 (+0.749952 px).
- **Finding**: The reorder landed and is jar-correct — our inner-scope DOT now
  declares `__init_NotShooting, Idle, Configuring`, matching
  `test-results/dot-cache/state/kejabo-83-vinu490/svek-1.dot:5-7`. The row did
  NOT move. Direct measurement: feeding the SAME captured inner `DotInputGraph`
  to `layoutGraph` (`src/core/graph-layout.ts` -> `@knowvah/dot-engine`) under
  both node orders returns identical `width` 129.6850758356914, `height`
  219.99996, and identical `labelX`/`labelY` on every edge. Our engine's label
  force-search does not react to declaration order; real graphviz's does.
- **Impact**: `plans/state-declared-size-fix/findings/G20-linetype-routing.md`
  marks kejabo-83 `status: resolved`, `confidence: high`, mechanism
  "node-declaration-order divergence". That mechanism is real and correctly
  evidenced — but its experiment ran BOTH inputs through real `dot -Txdot`,
  and our render path does not use real graphviz for layout. So the mechanism
  does not transfer: the residual +0.750 px is a dot-engine-vs-real-graphviz
  label-placement divergence, i.e. the class SI28 originally proposed and G20
  ruled out on evidence that only covered the real-graphviz side. Any future
  attempt on this row belongs upstream in `@knowvah/dot-engine`
  (`docs/graphviz-issues/`), not in `src/diagrams/state/`.
- **Confidence**: High (measured directly, both orders, same graph object).
