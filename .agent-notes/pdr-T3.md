## Observation: parity.json and the committed PARITY-SVG.md were already out of sync
- **Context**: pdr-T3's AC3 requires regenerating `PARITY-SVG.md` from the
  committed `parity.json` and verifying the diff against `git show
  HEAD:.../PARITY-SVG.md` touches ONLY the preamble block.
- **Finding**: on `pdr/T3` (branched from main), `tests/oracle/svg-conformance
  /parity.json` was last regenerated by commit `9a0ce1ea` (2026-09-08,
  `generatedAt: 2026-09-03T18:57:41.486Z`, 360 rows), but the committed
  `PARITY-SVG.md` was last regenerated by commit `7f22718f` (2026-07-31,
  `Generated: 2026-07-31T14:20:33.935Z`, 358 rows). No commit in between
  reran `npm run svg:dashboard` after regenerating `parity.json`. `parity.json`
  on disk is byte-identical to `HEAD` (I never touched its population), but
  regenerating the dashboard from it necessarily changes far more than the
  preamble: Generated timestamp, Surveyed count, every verdict tally, and the
  per-family/diverged/structural-match tables all shift with the newer data.
  `diff --stat`: 1 file changed, 207 insertions(+), 202 deletions(-) (427 ->
  432 lines) — not preamble-only.
- **Impact**: Nothing in the repo enforces "regenerate the dashboard whenever
  parity.json changes" (it is a doc convention only, `docs/svg-conformance.md`
  § Survey and dashboard). A future task that wants a true preamble-only diff
  on this file should first re-verify `parity.json`'s `generatedAt` against
  the committed `PARITY-SVG.md`'s `Generated:` line before assuming they are
  in sync. I proceeded with committing the fully-regenerated file (correct,
  matches current `parity.json`) rather than hand-patching only the preamble
  into a stale report.
- **Confidence**: High (verified via `git log -1` on both paths and a byte
  diff of `parity.json` against `HEAD`).
