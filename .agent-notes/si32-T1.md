**Frame, after assembly (verified, not assumed).** `materializeAutonom`
computes one `dx/dy` (`state-composite-geo.ts:160-161`) and applies it to
*both* children (`shiftGeo`, `:181`,`:187`) and transitions
(`shiftTransition`, `:182`,`:191`); `shiftGeo` recurses the same pair
(`:56-57`). `layout.ts#applyStateDocumentMargin` (`:261-268`) then shifts
every node and every transition by the identical `(dx,dy)`. So the whole
assembled `StateGeometry` is one absolute frame, and a clip is
translation-commutative with every shift on the path. That is why today's
single `buildCompositeAnchorRects(states)` over the top-level array
(`layout-ink-extent.ts:370`) already keys nested transitions correctly.

**Consequence for the D1 site.** Sites 3, 4 and 7 have no `StateNodeGeo`,
so per-site clipping is impossible there without materializing early —
which is the correct half of D1's argument. It is the *other* half that
fails, below.

## The failed premise — "before any consumer"

The ink walk is not a terminal consumer. It is called three times, and two
of those calls run **during** assembly and **feed back into node geometry**:

- `state-composite-concurrent.ts:190` — `const ink =
  computeSvekResultGeometry(states, transitions);` whose `width/height/dx/dy`
  become the region's stacking extent and position correction
  (`:196-199`, consumed at `:434-444`).
- `state-composite-autonom.ts:268` — `const geometry =
  computeSvekResultGeometry(inkStates, inkTransitions);` → `childImg`
  (`:269-272`) → `measureAutonomWrapper(s, childImg, …)` (`:274`) → the
  composite's own `width`/`height` in the **containing** pass.
- `layout.ts:262-263` — the only genuinely terminal one.

`buildInkBox` (`layout-ink-extent.ts:369-373`) builds
`buildCompositeAnchorRects(states)` and calls `addTransitionInk`, which
today clips (`layout-ink-transition.ts:147` → `clipTransitionPoints`,
`:116-127`). Retiring `clipTransitionPoints` in favour of a single pass
placed after `layoutFlat`/`layoutComposite` returns would leave calls 1 and
2 measuring **unclipped** splines — a behavioural change in the very numbers
that determine composite node sizes, and a divergence from upstream, where
`solve`'s clip loop precedes each level's own `SvekResult`
(`GraphvizImageBuilder.java:287-289`).

These two are not a hypothetical path. Reachability, checked structurally
then confirmed by running the public pipeline (probe deleted):
`state-composite-classify.ts:158` classifies a non-autarkic composite
`'cluster'`, and `resolveEndpoint` (`:254-256`) rewrites any endpoint
addressing it to `zaentId` = `__zaent_<id>` (`:246-248`). For
`state Outer { state Inner { I1; I2; I1-->I2 } state P; I1-->P; P-->Inner }`,
`layoutState` yields `Outer.transitions = [I1->I2, I1->P, P->__zaent_Inner]`
with `Outer.children = [Inner, P]` — i.e. the `__zaent_` edge and `Inner`'s
rectangle both sit in **Outer's own autonom pass**, so
`state-composite-autonom.ts:268` clips it today, before `Outer`'s size is
fixed. There is therefore no point in this pipeline that is simultaneously
after node geometry is final and before every clip consumer: a composite's
node geometry is *computed from* a clip consumer.

## Q4 (D5) — labels

**D5's conclusion holds; its stated reason is only half right.**

- Upstream: label position is `getXY(fullSvg, noteLabelColor)`
  (`SvekEdge.java:742-746`) — the graphviz label-node position, never
  `dotPath`. Clipping `dotPath` cannot move it. **D5 confirmed upstream.**
- This port: `attachInlineTransitionLabel` uses
  `edgeResult.labelX/labelY` (the engine's own `lp`) **only when
  `labelX !== undefined` AND a measurer is present**
  (`state-transition-label.ts:386-389`); otherwise it falls back to
  `perpendicularOffsetLabel(points)` (`:394`), which *is* derived from the
  point list (`:161-175`). `attachNoteOnLinkLabel` has the same two arms
  (`resolveNoteAnchor`, `:326-333`). The measurer-less arm is real:
  concurrent-region passes build their accumulator without font/measurer
  (documented at `:369-375`).
- So D5's premise "comes from the engine's own `lp`" is **not universally
  true** in this port. D5's *conclusion* nevertheless holds for any clip
  placed after construction, because `attachTransitionLabel` runs inside
  `buildFlatTransitionGeos` (`layout.ts:156`) and
  `buildLevelTransitionGeos` (`state-composite-pass.ts:347`) — the label is
  already fixed from the raw points before any such pass runs. The
  guarantee is **temporal, not structural**: a clip moved *into*
  construction (ahead of `attachTransitionLabel`) would move labels on the
  measurer-less path. Worth recording, since sites 3/4/7 are exactly the
  concurrent/spec paths where the fallback lives.

## The pass site D1 as written implies

If D1 were executed literally: `src/diagrams/state/layout.ts`, in
`layoutState`, on the value bound at `:255-257`
(`const raw = !hasAnyComposite(...) ? layoutFlat(...) : layoutComposite(...)`)
— i.e. **after `:257` and before `applyStateDocumentMargin(raw)` is called
at `:265`**. The pass must walk `geo.transitions` **and** recurse
`StateNodeGeo.children[].transitions` (and `concurrentRegions[].transitions`,
which share object identity with `children`'s — `state-geo-types.ts`
`StateNodeGeo.concurrentRegions`), keying against
`buildCompositeAnchorRects(geo.states)`.

That site satisfies Q1 and Q2 (node geometry is final and single-framed
there). It does **not** satisfy D1's own "before any consumer": the two
mid-assembly ink walks named above have already run and already shaped
`geo`. No workaround is proposed here.
