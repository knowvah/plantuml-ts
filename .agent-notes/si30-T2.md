## Observation: descAtomOps/titleAtomOps text-atom altitude wiring (SI30/T2)
- **Context**: Wiring `getStartingAltitude`/`getFont` (T1) into the two
  `AtomOps` implementations that drive `desc`'s real Sea/SheetBlock1
  pipeline (`EntityImageDescriptionDelegates.ts#descAtomOps`,
  `leaf-sizing-folder-title.ts#titleAtomOps`).
- **Finding**: `DriverTextSvg.draw` (`driver-text-svg.ts:135`, landed by T1)
  ALREADY mutes the font at actual render time via its own `getFont(font)`
  call. Upstream's `AtomText.drawU` mirrors this: `UText` is built from
  `useFontConfiguration` (`fontConfiguration.adjustColorForBackground(ug)`,
  java:205), which is UNMUTED (only color-adjusted) — the muting for
  on-screen size happens inside the SVG driver, not at `UText.build` time.
  So `descAtomOps#drawU`'s `UText.build(atom.text, atom.font)` call
  correctly stays UNMUTED; only the `measureLine` call that computes the
  `height - descent` baseline offset needs the muted font
  (`measuringFont(atom.font)`). Passing an already-muted `FontConfiguration`
  into `UText.build` would double-mute (the driver would re-apply
  `muteFontSize` on top of an already-shrunk size) if `fontPosition` were
  retained on the muted copy.
- **Impact**: Any future AtomOps/consumer wiring `getFont` must keep the
  UNMUTED `FontConfiguration` on the drawn `UText`/`UImage` shape and only
  mute at MEASUREMENT call sites (`measureLine`, `atomTextWidth`,
  `getDescent`) — mirrors D1's "read through `getFont` at every measure
  site" contract, not "store a muted config eagerly".
- **Confidence**: High (traced `AtomText.java:205-215`, confirmed
  `driver-text-svg.ts:121-150`'s existing SI30 comment, and verified via
  the `EntityImageDescriptionDelegates.test.ts` paired test: drawn
  `font-size="11"` for the EXPOSANT run while `calculateDimension`'s Sea
  placement independently derives height 17 from the same muted height).
