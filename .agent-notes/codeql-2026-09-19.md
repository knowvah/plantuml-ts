# CodeQL pass — 2026-09-19

## Observation: an unparseable skinparam color reached every `fill` attribute raw
- **Context**: Triaging CodeQL alert 13 (`js/html-constructed-from-input` on
  `svg.ts#svgRoot`). Probed with `skinparam backgroundColor x"onload="alert(1)`.
- **Finding**: `skinparam-key-normalize.ts#resolveColor` passed any token
  through verbatim; `resolveColorToSvgHex` keeps that by design (g1c K1,
  emission layer). The string landed unescaped in the canvas rect, the shell
  `style`, every arrowhead marker, and participant boxes. Upstream never
  gets there: `SkinParam#getHtmlColor` (SkinParam.java:371-396) runs
  `HColorSet#getColorOrWhite` (HColorSet.java:58-63) at the skinparam
  boundary, and the jar renders that source with `background:#FFFFFF`
  (oracle-verified). Fixed at the same boundary: `resolveColor` now applies
  `parseColor`'s (HColorSet.java:78-119) acceptance set, WHITE otherwise.
- **Impact**: K1 (verbatim at the EMISSION layer) is untouched. SI26's
  named divergence (arrowFontColor unset, not white) is preserved by gating
  `arrowFontColorValue` on the raw value. `skin-loader` and `skinparam`
  pins that read the raw token back from the theme now read `#FFFFFF`.
- **Confidence**: High.

## Observation: 39 attribute sinks bypass `attrs`/`attrsFromRecord`
- **Context**: Deciding where to escape for alert 13.
- **Finding**: `grep -rn '[a-z-]="\${' src` finds 39 template-literal
  attribute interpolations across 14 files (svg-markers.ts 8, svg.ts 6,
  svek-dot-emit-clusters.ts 4, ...), 15 of them color attributes. None
  escape. `formatAttrValue` (the declared "single point where an attribute
  value becomes text") does not escape either, and cannot be made to
  without first removing `linkWrap`'s pre-escape (svg.ts:401-402), which
  would otherwise double-escape. The jar escapes every attribute once, at
  DOM serialization (`SvgGraphics.java:598/882` + the XML transformer).
- **Impact**: With the skinparam boundary fixed, remaining user-text-to-
  attribute paths (inline `#color` tokens are regex-restricted to `\w`;
  `<img:…>`/sprite/`[[url]]` paths are NOT audited) are the open question.
  Filed in `planning/next-missions.md`.
- **Confidence**: High for the count; Medium for "no other path leaks" —
  not audited.

## Observation: `skinparam backgroundColor` cascades into participant boxes (fidelity, not security)
- **Context**: Oracle comparison while verifying the fix, `A -> B` with
  `skinparam backgroundColor red`.
- **Finding**: jar participant `<rect>` keeps `fill="#E2E2F0"` and the shell
  style is `background:#FF0000`; the port draws participants `fill="#F00"`
  and `background:red`. Two gaps: the theme cascades `backgroundColor` into
  sequence participant background, and the shell emits the raw name where
  the jar emits canonical hex (`HColor#toSvg`).
- **Impact**: Pre-existing, unrelated to CodeQL; filed in next-missions.
- **Confidence**: High (single oracle render, both differences visible).

## Observation: CodeQL cannot see `RegexConcat`-built patterns
- **Context**: Assessing whether the ported command grammar is exposed to
  the ReDoS class CodeQL flagged.
- **Finding**: All 13 alerts sat in port-local scaffolding (include
  prefetch, SVG assembly, sanitizer, scripts, a test). The runtime-composed
  command regexes are invisible to CodeQL's JS regex analysis, so their
  absence from the alert list is not evidence they are linear.
- **Impact**: A separate, deliberate ReDoS audit of `RegexConcat` output
  would need its own tooling (e.g. run each composed pattern through a
  static ReDoS checker at build time).
- **Confidence**: High.
