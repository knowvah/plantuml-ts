## Observation: mapping `ge.xlabel` onto `labelX`/`labelY` alone does not
## close pavuzo-79-zodu430's declared-width gap — a second echo bug exists

- **Context**: Step 3's acceptance criterion required pavuzo-79-zodu430
  scope2/width/idx2 to reach exact (0). After Step 2 (forward `xlabel` in
  `addEdges`) + Step 3 (map `ge.xlabel` in `toEdgeEntry`) alone, the row
  moved from `-2.460024px` to only `-1.579968px` — improved, not exact.
- **Finding**: `toEdgeEntry`'s label-box echo-back
  (`entry.labelWidth`/`entry.labelHeight`) read ONLY
  `inp.attributes.labelWidth`/`labelHeight`, never `xlabelWidth`/
  `xlabelHeight`. `moveLabelToXlabel` (both `state-dot-graph.ts` and
  `class-dot-edges.ts`) always deletes `label`/`labelWidth`/`labelHeight`
  when it sets `xlabel`/`xlabelWidth`/`xlabelHeight` — so for every
  xlabel-carrying edge, `entry.labelWidth` stayed `undefined` even after
  `entry.labelX` became defined. This gates OFF `canvasSize()`'s own
  `e.labelX + e.labelWidth / 2 + CANVAS_MARGIN` width-extension term
  (`graph-layout.ts:381`) for every such edge. Fixed by falling back to
  `xlabelWidth`/`xlabelHeight` in the same echo block (mirrors the
  `label`/`xlabel` mutual exclusivity already established for the position
  mapping). Verified via a dedicated unit test
  (`tests/unit/core/graph-layout.test.ts`, "echoes labelWidth/labelHeight
  from xlabelWidth/xlabelHeight...").
- **Impact**: real, independently-justified bug fix (not fixture-specific
  tuning) — `canvasSize()`'s own label-width term is now functional for
  every xlabel-carrying edge, not just plain-`label` edges. Re-measuring
  pavuzo-79-zodu430 after this fix showed **no further change**
  (`-1.579968px`, unchanged) — `canvasSize()`'s raw layoutGraph() width
  turned out NOT to be what feeds this fixture's declared composite width
  (see next note); the fix is still correct and worth keeping for whatever
  DOES read `layoutGraph()`'s raw canvas width directly (flat/non-composite
  callers).
- **Confidence**: High — isolated via a controlled unit test and a direct
  before/after fixture re-measurement.
- **Superseded**: this fallback was REMOVED from the tree by the
  coordinator before commit. Its own code comment claimed it was what
  drove pavuzo-79-zodu430 to exact — false; direct measurement (line above:
  "no further change") already contradicted that claim in this same note,
  but the comment in `graph-layout.ts` said it anyway. Measured both ways:
  0 of 2660 harness rows and 0 of 2017 rendered fixtures changed with vs
  without it. Unrequested by the task spec and provably inert corpus-wide,
  so it does not land. Do not re-add it, and do not restate the "only
  reaching 0 once this echo was added" claim anywhere — see the corrected
  diagnosis below for what the -1.579968px residual actually traces to.

## Observation: the "dot-engine matches native graphviz exactly" claim
## below was WRONG — corrected via a precision-controlled A/B

- **Context**: a first cross-check (reduced 2-node repro, hand-typed DOT
  with node width truncated to `1.2731`) appeared to show dot-engine's
  xlabel force-search byte-identical to native `dot -Txdot`. That
  conclusion was reported and is **retracted here**: the hand-typed repro's
  own truncated width was WRONG (jar's real cached value is `1.273090`,
  not `1.2731`), and dot-engine's own production output happened to match
  that SAME wrong precision — a same-error-on-both-sides artifact that
  looked like a fidelity proof but wasn't one. Caught by re-running the
  cross-check with jar's exact cached widths and comparing against
  dot-engine's OWN `getLayout()` output (full float precision, not
  text-serialized) for the SAME production graph, not a hand-typed one.
- **Finding (corrected)**: native `dot -Txdot`, fed jar's exact cached
  widths (`0.694444`/`1.273090`) for the Idle/Configuring/EvConfig
  sub-graph, reports `xlp="27,75.558"` (matches issue-16's OWN original
  filing quote exactly) and `xlp="43.667,60.442"`, `bb="0,0,108.16,192"`.
  The SAME graph built through this port's OWN `addNodes`/`addEdges` and
  read via `getLayout()` reports `xlabel={x:27,y:75.47}` /
  `{x:40.5,y:60.47}`, node centres at x=60.75, bb width=106.581. First
  edge's `xlp.x` matches (27); second diverges 3.17pt (40.5 vs 43.667);
  node centring itself diverges 1.58pt (60.75 vs 62.333) — NOT just the
  label, the real nodes shift too. Removing xlabel attrs entirely from the
  same native input drops bb to 91.662 (bare node width, centre 45.831):
  xlabels widen native's canvas/centring by +16.502pt vs this port's own
  +14.919pt on the identical input — @knowvah/dot-engine reserves ~1.58pt
  less room for `splines=ortho` xlabels than native graphviz 15.1.1 does.
  Traced the composite's declared width formula itself
  (`state-composite-autonom.ts#buildPlainAutonomSpec` →
  `computeSvekResultGeometry`/`measureAutonomWrapper`, read-only, gated
  `console.error` tracing added and reverted) and cross-checked it against
  jar's OWN Java (`SvekResult.java:130-133`, `InnerStateAutonom.java
  :186-195`, `XDimension2D.java:101-105 mergeTB`): the formula is
  byte-faithful (ink 106.5825 + 15 + 20 = 141.5825, matching measured
  "ours" exactly) — jar's own arithmetic is NOT the cause. Full four-part
  diagnosis artifact (mechanism/origin/causal chain/ruled out) written into
  `docs/graphviz-issues/TRACKER.md`'s issue-16 entry.
- **Impact**: the residual is a genuine `@knowvah/dot-engine` geometry gap
  in `splines=ortho` xlabel canvas reservation (its own `label/
  xlabels.ts`, porting graphviz's `dotgen/dotsplines.c` EDGETYPE_ORTHO
  branch + `common/postproc.c#addXLabels`), not a `~/git/plantuml` mismatch
  and not a bug in T1's own consumption seam. Not fixable within T1's
  write-set. Next step (not done here): file a new
  `docs/graphviz-issues/` entry with the native-with-vs-without-xlabel bb
  A/B as the repro.
- **Confidence**: High on the corrected numbers (direct instrumentation,
  reverted) and the ruled-out list; MEDIUM on whether the second edge's
  3.17pt xlp drift and the 1.58pt centring shortfall are one mechanism or
  two coincident ones inside dot-engine — not proven either way, flagged
  as the next instrumentation step.
