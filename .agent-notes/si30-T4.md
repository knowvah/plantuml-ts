## Observation: class member rows and notes need DIFFERENT dy references
- **Context**: Wiring `<sup>`/`<sub>` Sea `dy` into class member rows
  (`class-member-creole.ts#resolveMemberAtoms`) and notes
  (`renderer-note.ts#renderNoteLineAtoms`).
- **Finding**: The two class-engine render paths reconstruct a baseline
  from two DIFFERENT pre-existing references, and `dy` must correct
  against whichever one the renderer actually uses:
  - Notes: `lineTop + lineHeight - atom.font.size/4.5`, where `lineHeight`
    is a genuine per-line `Sea` height (`note-layout-measure-rows.ts
    #noteLineHeight`).
  - Members: `sectionTop + rowTop + baselineOffset`, where `baselineOffset`
    (`class-layout-header-geo.ts:240`, `fontSpec.size -
    measurer.getDescent(fontSpec, '')`) is a flat PER-CLASSIFIER constant,
    unrelated to any row's own content/height.
  Using the note-style (Sea-height) reference for members gives `dy=0`
  for a `<sup>`/`<sub>` line and silently drops the correction; using the
  member-style (baseFont-constant) reference for notes desyncs from
  `noteLineHeight`'s own value. Verified jar-exact for both once split
  (`class-member-creole-sea.ts#textAtomDy` vs `#noteLineAtomDy`).
- **Impact**: Any future work threading `Sea`/altitude corrections into
  BOTH engines from one shared primitive must keep two reference formulas,
  not one. `resolveMemberAtoms` is shared by class members AND notes
  (`note-layout-measure.ts#buildPlainRows` calls it directly) — its own
  `dy` field is member-flavored; `noteLineAtomDy` recomputes the
  note-flavored value separately from the same `MemberRenderAtom[]`.
- **Confidence**: High (jar-verified against `exposant-01-class`'s real
  `in.svg`, both member rows and the note line, byte-exact `y`/`font-size`
  down to the row containing BOTH `<sub>` and `<sup>`).

## Observation: dy's Sea coupling must be TEXT-ONLY, not all-kind
- **Context**: The first `<sup>`/`<sub>` dy implementation used ALL atoms
  (text + img/sprite/vector) in the `maxSpan` reduction feeding `dy`.
- **Finding**: A tall img/sprite/vector atom sharing a row with plain text
  (no `<sup>`/`<sub>` at all) silently shifted the TEXT atom's `dy` away
  from 0, because `maxSpan = max(height - altitude)` is dominated by the
  icon's real height even though its altitude is 0. jar-verified via
  `render-manifest`'s baseline: `cuzoga-39-tufu259`, `jevuvi-65-dipo437`,
  `rideze-59-lizu265`, `rotisi-30-loge424` (all icon-in-member-row
  fixtures, zero `<sup>`/`<sub>`) moved when the reduction included
  non-text atoms. Fix: `textAtomDy`'s (and `noteLineAtomDy`'s) `maxSpan`
  must be reduced over TEXT-KIND entries only — img/sprite/vector/bullet
  atoms are drawn via their own INDEPENDENT placement rule in both
  renderers (`renderRowAtoms`'s image/vector branches, `renderNoteLineAtoms
  `'s `legacyY`/bullet branches) and never read `dy`, so they must not
  perturb a text sibling's baseline through the Sea reduction. The ROW's
  own overall `height` (used for box sizing / row stacking) is UNAFFECTED
  by this — it still correctly uses ALL atom kinds (DOT-parity verified
  delta=0 either way).
- **Impact**: Any generalization of this Sea-dy pattern to another engine
  with mixed text+inline-atom lines needs the SAME text-only restriction
  on the coupling reduction, or it will silently perturb unrelated rows.
- **Confidence**: High (jar-verified via `render-manifest-baseline.json`
  diff — 4 unrelated class fixtures moved and un-moved exactly with this
  one change; `manifest-diff.py` gate green after the fix).
