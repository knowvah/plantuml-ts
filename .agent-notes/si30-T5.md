## Observation: expandRun width bug (state-sizing-creole.ts, pre-existing, fixed in T5)
- **Context**: Probing exposant-03-state's rendered SVG against the jar's own
  in.svg while implementing per-run size/dy drawing.
- **Finding**: `expandRun` (state-sizing-creole.ts) measured every run's own
  glyph width using the LINE's shared `font` (e.g. 14pt) instead of the
  run's own effective/muted `size` (11pt for a `<sub>`). The DECLARED box
  width was unaffected (state-sizing-creole.ts's `toStyledLine` sources
  `.width` from the seam's `CreoleTextLine.width`/`Sea.getWidth()`, which
  already used the correct muted size internally — this bug only affected
  the RENDER-time per-run width used for x-advance). Jar-probed:
  `measurer.measure('2', {size:11}).width` = 6.11875 (matches jar's own `O`
  x-position on exposant-03-state, x=28.269); pre-fix code measured 7.7875
  (the "2" at 14pt), landing `O` 1.669px too far right. Fixed by building a
  `runFont = {...font, size: run.size}` once per run and using it for every
  `measure()`/tab-stop call inside `expandRun` — matches `AtomText.java`'s
  own single-font-per-atom contract (`getWidth`/`drawU`/`getTabSize` all
  read `fontConfiguration.getFont()`, the atom's own).
- **Impact**: Any state description/note line mixing a `<sup>`/`<sub>` run
  with trailing NORMAL content would draw the trailing content offset by
  the mute delta's width difference. Now byte-exact against jar for both
  probed fixtures (juvagu-33-dupa212, exposant-03-state).
- **Confidence**: High (jar-verified via cached `in.svg`, both before/after).

## Observation: notes now draw resolved run color (manifest move outside allow-list)
- **Context**: `renderer-note.ts#renderNoteTextLines`/`renderNoteOnLinkTextLines`
  rewritten to draw per-run via `renderStateRuns` (reusing the header/body
  emitter) instead of one joined `<text>` per line, per T5's explicit scope
  ("notes draw the SAME runs, size/dy").
- **Finding**: the PRE-T5 note renderer hardcoded `fill: '#000000'`
  unconditionally, ignoring any creole-resolved run color entirely (the
  module's own doc comment named this: "per-run color/bold/italic
  decoration is NOT drawn"). `renderStateRuns` correctly applies
  `run.color ?? style.fill`, so a note using `<color:...>` now draws with
  the real color instead of always black — a genuine fidelity improvement,
  but an unavoidable side effect of getting size/dy through the SAME shared
  emitter (there is no way to thread only size/dy without also getting
  color/bold/italic/underline, since `StateTextRun` bundles all of it).
- **Impact**: `render-manifest`'s SHA-256 for `xeziki-47-zomo866` (state,
  `<color:...>` note body) moved — NOT on `plans/creole-exposant-port/
  expected-moves.txt`'s allow-list (only exposant-01-class/02-usecase/
  03-state + juvagu-33-dupa212 are listed). `manifest-diff.py` reports this
  as 1 unexpected move (plus a SEPARATE unexpected move on
  `sovuxo-25-tepi226`, class engine, T4's territory — not diagnosed here).
- **Confidence**: High (mechanism traced to the exact hardcoded literal
  removed; jar itself DOES apply per-run note color, so this is a move
  toward jar, not away from it).
- **Disposition**: Reported as a STOP in the T5 close-out rather than
  silently editing `expected-moves.txt` (not in T5's write-set) or reverting
  the fix (would mean keeping a known, doc-flagged rendering gap alive
  purely to dodge a ratchet file). Orchestrator to decide: widen the
  allow-list, or scope note-color drawing out of this task.
