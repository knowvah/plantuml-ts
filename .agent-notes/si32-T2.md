# SI32 T2 — clip once, per layout result

## Observation: the state clip now lives at construction, one call per layout result
- **Context**: porting `DotStringFactory#solve`'s edge loop under D1'/D2'.
- **Finding**: two call sites, one per `TransitionGeo` construction path —
  `state-composite-pass.ts#buildLevelTransitionGeos` (composite; all seven
  entry points funnel through it) and `layout.ts#buildFlatTransitionGeos`
  (flat). `layout-ink-transition.ts#clipTransitionPoints` and
  `#buildCompositeAnchorRects` are gone, and `addTransitionInk` /
  `addNodeInk` / `buildInkBox` no longer thread an `anchorRects` argument.
  The arithmetic is still the single core port `src/core/spline-clip.ts`;
  the new module `state-transition-clip.ts` is wiring only.
- **Impact**: measure and draw now read the same curve, as upstream does.
- **Confidence**: High.

## Observation: the flat pipeline can never clip
- **Context**: wiring the flat half of the loop.
- **Finding**: `state-dot-graph.ts#buildDotGraph` emits no clusters at all, so
  `result.clusters` is absent and `clusterAnchorRectsOf` returns the empty map;
  no `__zaent_` endpoint can exist there either (`resolveEndpoint` runs only in
  the composite pass). The flat call is a structural no-op today, wired for
  symmetry with upstream's unconditional one-`solve()`-per-layout-result shape.
- **Impact**: a future flat-path cluster would clip for free; nobody should
  "optimise" the call away as dead.
- **Confidence**: High.

## Observation: the `__zaent_` -> cluster-box join is 1:1 and holds under shift
- **Context**: D2' requires keying clip rects off `result.clusters`.
- **Finding**: `state-composite-cluster.ts:458-459` pushes `zaentId(s.id)` onto
  its OWN composite's `DotInputCluster.nodeIds`, and that is the only place any
  `__zaent_` id enters a `nodeIds` list (`applyBorderPointRanks` puts the
  anchor on `portAnchorId`/`portRanks`, never `nodeIds`; a nested cluster child
  is excluded from its parent's `nodeIds` by
  `state-composite-cluster.ts:436-438`). `result.clusters` is keyed by the same
  `DotInputCluster.id`. Verified by probe on three shapes: `fovafu-44-mifu394`
  (1 cluster), `temuxi-28-cega322` (nested, 4 clusters, 1 anchor -> cluster0)
  and `giniti-22-fexo000` (concurrent + nested, 3 anchors -> cluster1/2/3 with
  correctly nested boxes). `shiftDotLayoutResult` translates `clusters`,
  `nodes` and `edges` together, so the two shifted call sites stay in frame —
  observed directly (`fovafu` cluster box x=-24 raw, x=7 shifted, matching the
  edge shift).
- **Impact**: no re-basing is needed at any call site, and no second seam.
- **Confidence**: High.

## Observation: upstream does NOT always clip against the raw graphviz cluster box
- **Context**: coordinator correction to D2', re-read against the Java.
- **Finding**: `DotStringFactory.java:424-434` sets `cluster.setPosition(min,
  max)` from the graphviz polygon, and `Cluster.java:511-513` makes that
  `rectangleArea` — which IS `result.clusters`, so D2' is right in general.
  But `SvekEdge.java:660-663` calls `projectionCluster.manageEntryExitPoint(
  stringBounder)` immediately before the clip at `:671-672`, and
  `Cluster.java:409-436` REASSIGNS `this.rectangleArea =
  frontierCalculator.getSuggestedPosition()` (with
  `ensureMinWidth(getTitleAndAttributeWidth() + 10)` when the cluster is
  titled). `projectionCluster` is set only for composites with border-point
  children — `ClusterDotString.java:101-105`, gated on
  `entityPositionsExceptNormal().size() > 0`, applied to every line
  `isLinkFromOrTo` that cluster. It is order-dependent mutation of shared
  cluster state inside the per-line loop: a later line whose `lhead` is the
  same cluster sees the already-adjusted rect.
- **Reachability, measured**: of the 41 fixtures whose clip fires, exactly two
  have a clipped-anchor composite with a direct border-point child —
  `pesita-10-dene726`'s `AA` (`aa_ok_ex <<exitpoint>>`) and
  `viroxo-69-fito663`'s `comp1` (`ex <<exitpoint>>`). Determined with the
  port's own `hasDirectBorderPointChild`, not by reading the `.puml`.
- **Measured effect** (shift-invariant, raw box vs the frontier-adjusted box
  `state-composite-geo.ts#borderPointBox` already computes): `AA`
  156x118.720012 vs 126x104.720 — 30 px wider, 14.000012 px taller; `comp1`
  123x277.000016 vs 109x277.000016 — 14 px wider. Both fixtures still move
  TOWARD the jar (-163.97 px and -44.04 px summed endpoint error), so this is a
  residual, not a regression. The clipped edges' own residuals (25-45 px) sit
  in the same band as the UNCLIPPED edges in the same fixtures
  (`aa_ok_ex-to-Idle` 39.33, `nasreq_auth-to-*end*nasreq_auth` 44.94, both
  unchanged), so this metric cannot separate the rect gap from those fixtures'
  pre-existing positional error.
- **Impact**: DIVERGENCES.md candidate for T3. Porting `manageEntryExitPoint`
  into the clip is a separate mission — it needs the per-line projection
  cluster and the mutation ordering, not just the arithmetic (which this port
  already has).
- **Confidence**: High.

## Observation: `mefici-97-tudu030` IS canvas-exact (T2's measurement was wrong)
- **Context**: T2 recorded, at High confidence, that ours is 820x673 against
  the jar's 816x673 — a "pre-existing 4 px width residual".
- **Finding**: **that is incorrect.** Orchestrator re-measured on this tree via
  two independent render paths (bare `renderSync` + `DeterministicMeasurer`,
  and the same wrapped in `withStdlib(buildStdlibAssetsStore())` — the exact
  `scripts/render-manifest.ts#renderFixture` wiring). Both emit
  `width="816px" height="673px"`; the jar's `in.svg` emits the identical
  string. Also measured 816x673 pre-change at `4895623b` and at SI31's own
  `235ddbe2`. All four no-headroom fixtures are canvas-exact, as the task file
  stated.
- **Impact**: the erroneous version would have told a future task that
  mefici's width is NOT locked-exact — the exact inverse of the truth, and an
  invitation to "improve" a row that is already on the jar. Corrected here and
  in `expected-moves.txt` before it could reach the close-out.
- **Confidence**: High (two render paths, two commits, byte-compared against
  the jar's own `<svg width/height>`).
