# The `parity-*.json` pins carry weeks of un-adopted drift

Written 2026-09-03 during mission `linetype-ortho-routing` T8, which had to
re-pin `parity-state.json` and discovered this on the way. **Not caused by
that mission** — the disproof is below. Filed separately because it needs an
owner and the linetype mission is not it.

## Observation: regenerating `parity-state.json` changes 174 of 271 entries

- **Context**: T8 re-pins the 8 fixtures whose jar DOT carries `splines=`.
  The supported regeneration is whole-file
  (`svg-parity-survey.ts --out ... state`), so a fresh run was needed to get
  correct values for 2 of them.
- **Finding**: the fresh survey differs from the committed pin on **174**
  fixtures — 2 of them this mission's, **172 not**. Six entries flip
  `dotEqual`, of which **two go `true` → `false`**:
  `lurage-50-kobo763` and `xetase-70-zaza808`. Four go `false` → `true`
  (`zecivu-62-pagu681`, `fugedo-34-fice721`, `xacona-99-peze211`,
  `cagego-53-vemo516`) — improvements nobody has banked.
- **Impact**: the committed pin's `generatedAt` is **2026-08-12**. Every
  mission since has moved state geometry without re-pinning this file, so it
  describes a tree three weeks gone. Anyone re-pinning it as a side effect of
  unrelated work silently adopts all 174 — including the two regressions —
  under their own mission's name.
- **Confidence**: High. Measured both ways.

## Why `linetype-ortho-routing` is provably not the cause

Not an alibi — a mechanism. This mission's only behavioral change is
`dotSplinesAttrs(input.linetype)`, which returns `[]` when `linetype` is
`undefined`. `DotInputGraph.linetype` is set only from `theme.linetype` /
`ast.linetype`, which are set only by `skinparam linetype ortho|polyline`.
A fixture whose source has no `linetype` therefore emits a byte-identical
DOT and lays out identically.

**Of the 172 outside-the-8 movers, `linetype` appears in the source of
ZERO.** All six `dotEqual` flips are likewise `linetype`-free. The change
cannot reach them.

Independently corroborated: `measure-class-size-deltas.ts` was byte-identical
across all 714 class fixtures before and after this mission's class change,
and a direct 8-fixture sweep found the 6 non-state fixtures bit-identical
after T4.

## What T8 did about it, and why

**Re-pinned the 8 surgically; did not adopt the other 172.** Adopting them
would violate the mission's own headline rule — *every fixture that moved is
named with a mechanism* — since no mechanism can be named for fixtures this
mission never touched. It would also bury two real regressions inside a
commit about splines.

This resolves a tension inside the brief itself: `batch-4/overview.md` says
"re-pin what actually moved, and only that", while T8's quality bar says
"re-pin unconditionally, every fixture". The quality bar's own rationale is
the activity mission's lesson — that incremental scripts left *in-scope*
pins stale. Surgical-but-unconditional-within-scope satisfies both: all 8
re-pinned from a fresh measurement whether or not each moved, nothing
outside adopted.

## For whoever picks this up

1. `lurage-50-kobo763` and `xetase-70-zaza808` are **`dotEqual` regressions**
   of unknown origin, live in the tree today. Neither is currently visible,
   because the pin still says `true`. Bisect them first.
2. Four fixtures have silently become `dotEqual` and are not being credited.
3. `parity-class.json` and `parity.json` are the same age and were
   regenerated by T8 for comparison. **Measured, not extrapolated**: class
   differs on **300 of 722** rows with **27** `dotEqual` flips (one of them
   `true` → `false`: `tunelu-64-xica833`); component/usecase differs on
   **287 of 358**. Combined with state, that is **761 rows** of un-adopted
   drift and **three** `dotEqual` regressions across the three files
   (`lurage-50-kobo763`, `xetase-70-zaza808`, `tunelu-64-xica833`).
4. The general hazard is already recorded as "re-pin script raises a
   pre-existing red pin". This is the same failure with a different trigger:
   not an incremental script, but a **whole-file regeneration** of a pin
   nobody has refreshed in weeks. A whole-file re-pin is an adoption
   decision about every row in the file, not just the ones you came for.

## CORRECTION 2026-09-04 — "three regressions of unknown origin" was wrong

Appended after `doteq-regression-bisect` T0 diagnosed all three. The
*count* and the *recommendation* in this note stand; the **characterisation
does not**.

`lurage-50-kobo763`, `xetase-70-zaza808` and `tunelu-64-xica833` are **not
`src/` regressions**, and their origin is not unknown. `labelSizeOk` was
added to `tests/oracle/svek-dot.ts#compareStructural` at `d3ff29be`
(2026-08-15), **three days after** these pins were generated. It compares
each edge-label `<TABLE>`'s FIXEDSIZE `WIDTHxHEIGHT` as a multiset; the old
comparator checked only label *presence*. All three fixtures' label boxes had
already differed from the jar's before the pin was taken — the old comparator
could not see it, so the pin recorded `true`.

The bisect's own 2×2 is decisive: under either FIXED definition of
`dotEqual`, the verdict is identical at both ends of the window. Bad-end
`src/` with the old comparator reads `true`; good-end `src/` with today's
comparator reads `false`. The flip tracks the comparator, not the code. All
three are already-named residuals in the edge-label-box label-size backlogs.

So they belong to the **same** category as the other 758 stale rows — a pin
older than the thing that reads it — not a separate, more alarming one. That
mis-framing is what set the bisect mission's premise, and cost it a
three-worktree setup for a window with nothing in it.

**Re-pinned to `false` on 2026-09-04** (`67d8355e`), which is what they
measure. The remaining **758** rows are still un-adopted and still want an
owner; that part of this note is unchanged.

**The lesson generalises past this file.** Three times in two days a number
moved because the *instrument* changed, not the code: this, the `~0.002 px`
replay artifact, and `jakapi-64-tine258`'s `maxDelta` rising because a
structural improvement let the comparator descend past a `childCount`
short-circuit. Before attributing any pin delta to the port, check whether
the thing doing the measuring moved first — and note that a pin's
`generatedAt` is a claim about the comparator of that date, not just the
tree.

## CLOSED 2026-09-05 — pins refreshed, and the count here was wrong

All three files regenerated from one fresh survey (`41b002f5`); **753 of
1,351 rows** adopted. The open item this note raised is closed.

**The "three regressions" figure in this file is an under-count.** The real
figure at filing was **eleven** — 2 state, 4 class, 5 component. It reached
this note as 3 because the class listing was read from a truncated debug
print (`flips[:12]`) and the component corpus was counted for movers without
its `dotEqual` flips ever being enumerated.

Three were then diagnosed and re-pinned (`lurage-50-kobo763`,
`xetase-70-zaza808`, `tunelu-64-xica833` — comparator staleness, not
regressions). The remaining **8** are now pinned `false` and filed by name,
undiagnosed, in `.agent-notes/parity-repin-2026-09-05.md`. Start there.
