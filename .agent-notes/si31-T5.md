# SI31 T5 — G15 composite-anchor spline clip

## Observation: `simulateCompound` is a shared svek seam, now in `src/core/`
- **Context**: T5 needed the state engine to clip cluster-sourced splines; the
  only faithful port of `DotPath#simulateCompound` lived in
  `src/diagrams/description/spline-clip.ts`, which `layering.test.ts` Rule 2
  forbids state from importing.
- **Finding**: the file moved unchanged to `src/core/spline-clip.ts`. Its only
  dependency was a `Bbox` **type** from description's `layout-helpers.ts`; it
  now declares its own structural `ClipRect` (upstream's `RectangleArea`,
  which is literally what `SvekEdge.java:671-672` passes), so core keeps no
  dependency on `src/diagrams/`. `subdivide`/`clipSplineStart`/`clipSplineEnd`
  are byte-identical — no arithmetic changed.
- **Impact**: any future engine that needs compound-edge clipping imports it
  from core. There is exactly ONE port; copying it is forbidden (CLAUDE.md, D9).
- **Confidence**: High — the move was proven inert before the consumer landed
  (0 harness rows and 0 of 2017 render-manifest fixtures moved).

## Observation: `layout-ink-extent.ts` was at the 500-line hook cap
- **Context**: the file sits at 529 lines at HEAD (T4's south-cap term). The
  complexity hook's file check is directional against the git-HEAD baseline —
  an already-oversized file may be edited but never made longer.
- **Finding**: the transition-ink path was extracted to
  `src/diagrams/state/layout-ink-transition.ts`, taking the `InkBox` /
  `newInkBox` / `addPoint` primitives with it so the new module can be imported
  by `layout-ink-extent.ts` without a cycle. That is exactly the arrangement
  the class engine already has (`class-ink-shapes.ts` owns the primitives,
  `class-ink-box.ts` owns `buildInkBox`). `layout-ink-extent.ts` is now 482
  lines — back under the cap, not merely non-growing.
- **Impact**: further state ink work has ~18 lines of headroom in
  `layout-ink-extent.ts` and a clean home for transition-side terms. T4's
  `addSouthCapInk` was not touched.
- **Confidence**: High.

## Observation: the ink walk clips the spline, the state renderer still draws it raw
- **Context**: upstream clips `dotPath` ONCE in `SvekEdge#solveLine`
  (`:671-672`), so every downstream consumer — the drawn path and every
  extremity at `:681-735` — sees the clipped curve.
- **Finding**: T5's write-set was the ink walk only, so the clip is applied to
  the ink FOLD alone. `transitionArrowheadInk` still reads the raw
  `transition.points`, deliberately: the state renderer also still draws the
  raw path, and folding a clipped-derived arrowhead would reserve ink for a
  marker that is not painted there.
- **Impact**: a follow-on should clip the DRAWN path at the geometry source
  (one clip, as upstream does) and then drop the raw-points arrowhead caveat in
  `layout-ink-transition.ts`'s doc comment. Until then a state composite's
  outgoing spline can visually overshoot the cluster border by the amount the
  jar trims. Checked on all four moved fixtures: no real on-curve ink falls
  outside the (now narrower) canvas — the apparent overflow on
  `mefici-97-tudu030` is a bezier CONTROL point at x=858.995 whose curve peaks
  near x=838, inside the 854 canvas.
- **Confidence**: High for the mechanism; Medium for the corpus-wide claim
  (measured on the 4 fixtures that move, not on all 2017).
