## Observation: the jar draws an unresolvable colour token as WHITE; this port drops it (keeps the default)
- **Context**: SI26 fix(T1) — `skin reddress` reaches the skinparam accumulator with its `!define` macros unexpanded (`skin-loader.ts` runs `parseStyleBlock`/`resolveSkinparam` on the raw skin text), so `arrowFontColor ARROWFONTCOLOR` and `arrowColor ARROWCOLOR` arrive as literal words (arrowheads already draw `fill="ARROWCOLOR"`).
- **Finding**: oracle experiment (`skinparam arrowFontColor FOOBAR` / `arrowColor BAZ`, pinned jar) → the label AND the arrow draw `#FFF` (`HColorSet#getColorOrWhite`). The port's `style-cascade-class.ts#cascadeHex` and (since fix(T1)) the `arrowfontcolor`/`defaultfontcolor` handlers instead leave the field unset (default `#000000`) — a documented divergence choice (N36 rationale: an unresolvable raw string in `fill` is worse than the default). Also: the pinned jar has no `reddress.skin` (only debug/plantuml/rose/sonyxperiadev/strictuml), so `skin reddress` cannot be oracle-rendered at all.
- **Impact**: any future "make skins faithful" work needs `!define`/`!ifdef` expansion in `skin-loader.ts` first; and a colour-resolution divergence exists wherever the port guards unresolvable tokens.
- **Confidence**: High.
