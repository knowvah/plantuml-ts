## Per-mechanism detail

### 1. `description` swallows a tab-indented `title` line (5: dunila, gipeda, toxeto, xapuji, zetedu)

Exemplar `dunila-61-licu078`. Source is four `skinparam rectangle<<X>> {...}`
blocks, a tab-indented `title produces a green rectangle`, and
`rectangle  "C1"  <<GreenContainer>><<RedContainer>>  as C1`. Refusing line
(content-array index 0, the title line itself once `linePositions` maps it
back to raw source line 29): `descriptionPlugin.parse` returns
`{ kind: 'syntax', line: 29, consumed: 1, message: 'Syntax Error?' }`.
Isolated: `matchAnnotationCommand(['\ttitle produces a green rectangle'], 0,
...)` returns `null` (the tab defeats `TITLE_RE`'s `^title` anchor);
`matchAnnotationCommand(['title produces a green rectangle'], 0, ...)`
(no tab) matches. `class`'s own refusal for the same source (`execution`,
"Use 'allowmixing'...", score 300) is faithful and higher-scoring than
state's absence-of-refusal, so `state` — which has no `title` handling
sensitive to this bug — wins the source by default, landing STATE instead of
DESCRIPTION. Verified `parseNameSection` already parses the
double-stereotype rectangle line correctly in isolation (`stereotype: [
'GreenContainer', 'RedContainer' ]`), so the ONLY blocker is the title line.
Ruled out: not a stereotype-grammar defect (parses fine alone); not a
`rectangle`-command defect (same). Fix: trim the line passed to
`matchAnnotationCommand` inside `description`'s `dispatchCommand`, mirroring
`state`'s `nonBlankLines` precedent (`state/parser.ts:147-164`). D3: with the
title line recognised, the whole 2-line body parses clean and description
wins outright (no other candidate scores higher), landing DESCRIPTION.

### 2. `class` silently swallows an unopened/mis-opened container body (2: nicere, xipane)

Exemplar `nicere-96-keje834`: `action action { action action1 action action2
} process process { ... }`. `classPlugin.parse` returns NO refusal;
`classifiers` is `[{ id: 'action', kind: 'descriptive' }]` — IDENTICAL
whether or not the nested `action action1`/`action action2` lines are
present (isolated A/B test). Standalone, `action action1` (no braces) IS
correctly refused (`execution`, "Use 'allowmixing'..."), so the allowmixing
gate itself works; the defect is that container-body lines never re-enter
it. Mechanism: `class-command-containers.ts`'s rule 5b' — the real
`CommandPackageWithUSymbol`-mirroring container-open command, which DOES
call `openNamespaceBlock` and would let subsequent lines re-enter the
per-line/gate loop — only matches
`rectangle|node|component|folder|frame|cloud|database|storage|artifact|file|card|queue|stack|hexagon|agent`
(`class-command-containers.ts:89-90`). `action`/`process` are absent from
THIS list even though they ARE present in `CONTAINER_KEYWORD`
(`class-descriptive-leaf-command.ts:50-51`, documented as
`CommandPackageWithUSymbol`'s own SYMBOL alternation verbatim). So `action
action {` falls through to `DESCRIPTIVE_LEAF_COMMANDS` (rule 9), whose
`isContainerOpener` exemption (`class-descriptive-leaf-command.ts:112`) lets
it claim the line via `parseClassifierDecl`/`applyClassifierDecl` — WITHOUT
ever pushing a namespace, so the loop treats `action action1`,
`action action2`, `}` as ordinary top-level lines that get silently ignored
(no command matches `}` with no open scope either, but `closeBraceScope`
appears to no-op rather than refuse). `xipane-40-dune740` reaches the SAME
silent-drop outcome via a DIFFERENT trigger: its outer `rectangle "...
{$multi-quote}..." as he #white {` line DOES match rule 5b' (the keyword IS
present) and DOES open a real container, but the nested
`rectangle "**p-name**...""<h1 class=...">..." as pn #orchid` line's
triple-quoted juxtaposed-string form doesn't match ANY class command's
CODE/DISPLAY capture (isolated test: a SIMPLE nested `rectangle "pn" as pn`
line inside the SAME container IS correctly refused via the allowmixing
gate — only the complex-quote form is silently skipped). Both share the
mechanism this file's own doc comment already names for a prior fix
(`class-command-containers.ts:92-99`, the `component C1 $tag1 {`
precedent, jebovo-64-rasa849/sodoza-93-nanu557): an unmatched line inside an
open container must be refused (upstream's `getCandidate()==null` SYNTAX_ERROR,
`PSystemCommandFactory.java:169-175`), not silently ignored. Ruled out: not
an allowmixing-gate defect (the gate itself is correct when reached); not a
lollipop/relationship-parser defect (different command family). D3: for
`nicere`, once rule 5b' also matches `action`/`process`, the container opens
for real, `action action1` re-enters the loop, hits the SAME allowmixing gate
that already refuses it standalone, the whole class attempt aborts, and
description (verified via isolation to accept the top-level `action`/
`process` keywords generically) wins — landing DESCRIPTION. For `xipane`,
description's `parseNameSection` already handles the triple-quoted form (not
independently re-verified in this pass — flagged for the batch-2 executor);
if class is made to refuse-on-unmatched-body-line generically, the same
fall-through applies.

### 3. `class`'s lollipop link auto-creates its "existing" side (1: vagipu)

`B1 -() A1 / B2 -() A1 / B2 -() A2`. `classPlugin.parse` accepts, creating
4 ordinary classifiers + 3 lollipop circles. `class-lollipop.ts:196-201`'s
own doc comment states the mechanism verbatim: upstream's
`CommandLinkLollipop` requires the "existing" side (`B1` on line 1) to
already be declared, erroring `"No class X"` otherwise; this port
"leniently auto-creates" it instead, "consistent with every other
relationship-endpoint site in this parser." Since `B1` is never declared
before line 1, upstream refuses immediately (aborting the whole class
attempt), and description — independently verified to accept the identical
3 lines, auto-creating `B1`/`A1`/`B2`/`A2` as `interface`-symbol nodes with
links — wins. D3: matches the jar's DESCRIPTION exactly.

### 4. `sequence`'s note command doesn't register participants (4: covipu, jogaji, katoke, xurozi)

Exemplar `covipu-77-jimo313`: `note over IT, FKM: ... end note` is the
ONLY content. `sequencePlugin.parse` refuses `{ kind: 'incomplete', message:
'Sequence diagram has no participants' }` (`sequence/parser.ts:306`,

`command-note-factory.ts`'s `noteCommand.execute` calls `emit(state, ev)`
with the note's `participants: string[]` but never registers those names
as diagram participants. Upstream's `FactorySequenceNoteCommand` calls
`diagram.getOrCreateParticipant(location, ...)` for each name

consumed=1) and `xurozi-64-zaci349` (multi-line, single participant `Bob`,

`isIncomplete` check, never at the note-parsing itself. D3: once the note
command registers its referenced entities, `isIncomplete` is satisfied and

### 5. bare `note left` (1: teoz-ng-001-17) — mechanism not fully isolated

own refusal is `kind: 'syntax'`, not `incomplete`); not a note-position

not obviously explain bare acceptance — the exact upstream command/path was
NOT isolated this pass. Instrument next (for the batch-2 executor): bisect
against the real jar with a minimal `note left` + `end note` fixture,
varying whether a prior `participant`/message exists, to find which command
claims it.

### 6. `sequence` accepts a stereotype in a token position upstream refuses (1: pacope-41-pufu938)

Six `database "DB N" <<...>> as DbN`-shaped declarations plus a `sprite`
block. `sequencePlugin.parse` accepts the WHOLE source with no refusal.
Verified against the real jar (`scripts/oracle-render.sh`, three isolated
2-line probes): `database "DB 2" <<&file>> as Db2` (icon glyph
stereotype), `database "DB 2" <<$SpriteUsb>> as Db2` (sprite-name
stereotype) and `database "DB 2" <<plain>> as Db2` (plain-text stereotype)
ALL render `DESCRIPTION` — confirming the refusal is the TOKEN ORDER
(quoted-display, then `<<...>>`, then `as alias`), not the stereotype's
content. `database Db2 <<plain>>` (unquoted, no `as`) renders `SEQUENCE`.
`CommandParticipantA3.java:51-64` is the only `CommandParticipant` subclass
carrying a STEREOTYPE slot at all, and its grammar is `TYPE FULL(unquoted)
"as" CODE STEREO?` — stereotype AFTER `as CODE`, never between a quoted
display and `as`. `sequence-parse-helpers.ts:318`'s `parseParticipantDeclaration`
is a single shared parser with no such ordering restriction. Ruled out: not
a sprite/icon-specific gap (plain-text stereotype fails identically); not an
`isIncomplete` issue (6 participants would satisfy it regardless). D3: once
this specific line refuses, the whole sequence attempt aborts on line 2 and
falls through — matches the jar's DESCRIPTION (not independently
re-verified which candidate ultimately claims it for THIS specific 7-line
source, only that upstream's sequence factory itself refuses the isolated
2-line reproduction).

### 10. `class` claims a bare URL as an implicit classifier (1: zolaza-45-sepi570)

Single line: `https://forum.plantuml.net/17007/how-we-can-disable-textlength-at-svg-generation`.
`classPlugin.parse` accepts with no refusal, producing `classifiers: [{ id:
'https', kind: 'class', members: [{ name:
'//forum.plantuml.net/17007/how-we-can-disable-textlength-at-svg-generation'
}] }]` — the class-diagram colon-shorthand member command
(`class-member-parser.ts`, upstream `BodierLikeClassOrObject.java:102-111`'s
member-shorthand `isMethod`/`addFieldOrMethod`) splits on the URL's first
`:` and treats `https` as an implicit classifier id with one bogus member.
Jar routes this to STATE, so upstream's equivalent colon-shorthand command
(also registered on `ClassDiagramFactory`) must refuse a bare, undeclared,
content-free id this way, deferring to state's own bare-identifier fallback.
The exact upstream refusing command/line was NOT exhaustively traced this
pass (ruled out: not an allowmixing refusal — class produced a real
classifier, not an `executionRefusal`; not a sequence-side defect — sequence
already refuses this source correctly). Pinned rather than fixed: narrowing
class's colon-shorthand command to refuse a bare undeclared URL-shaped id
would need proving safe against every other single-line `Name : member`
fixture in the corpus (D9, narrow-never-widen) — a corpus-wide pass, not a
one-row special case.
