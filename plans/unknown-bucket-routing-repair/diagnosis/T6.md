# T6 — jar-NONE cohort (36)

`cohorts/T6.tsv`'s 36 fixtures all open `@startuml` (35) or `@startdef` (1)
and the jar's golden carries no root `data-diagram-type` attribute. The
brief's own framing — "the jar rendered these WITHOUT an error page" — is
**only true for 24 of the 36**. Re-measuring every golden over its FULL
byte length (not the 4096-byte head both gates' `isJarErrorPage`/`readHead`
read) found that **12 of the 36 are genuine jar `PSystemError` pages**,
misclassified `jarErrored: false` by the measurement tool because
`PSystemError#getTextBlock` (`PSystemError.java:213-231`) unconditionally
prepends a "Welcome to PlantUML!" tutorial block whenever
`source.getTotalLineCountLessThan5()` (`:217-218`) — true for every
fixture in this cohort, whose bodies are 1-2 lines — pushing the
diagnostic `PlantUML version ...` signature (`PSystemError.java:148`) past
byte 4096. This is a measurement-tool artifact, not a product gap; see the
"jar-error-beyond-head-window" row below.

## Mechanism paragraphs

### 1. Jar error page hidden past the head window (12: bupexo, dobujo,
fikaka, kokote, komoso, kutazo, nifosu, tumepe, zelini, zetebu, zicejo,
zodude)

Re-scanning each golden's FULL bytes (not the 4096-byte head) for the same
`PlantUML version [^<]*\[[^<]*\]|An error has occurred[^<]*` marker both
gates already use found it present — just past byte 4096 — in all 12. The
exemplar, `zodude-13-tito074` (`block Hello\nblock World1\n...`, an
unported block-diagram syntax), carries the marker at byte offset 7443 of
15192: `PlantUML version $version$ / $git.commit.id$ [Unknown compile
time]`, `[From in.puml (line 2) ]`, `@startuml`, `block Hello`, **`Syntax
Error? (Assumed diagram type: sequence)`** — a genuine `ErrorUml` page,
preceded by a 6.5 KB base64 donation-ad PNG (`PSystemError.java:221-229`'s
`addMessagePatreon`/`addMessageDedication`, gated on
`System.currentTimeMillis()`'s minute — NOT frozen by
`-DPLANTUML_DETERMINISTIC_TEXT=true`, which is why some of the 12 show the
ad and some don't) plus the mandatory Welcome-tutorial block
(`addWelcome`, `:255-262`, fired because `getTotalLineCountLessThan5()` is
true for every 1-3-line fixture in this whole cohort). This port's own
`weErroredIn` scans the WHOLE document (no truncation) and correctly finds
its own error banner for all 12 — the disagreement is entirely an
artifact of `isJarErrorPage`'s/`readHead`'s 4096-byte `HEAD_BYTES`
constant, shared by `scripts/pin-corpus-tree-measure.ts` and
`refusal-coverage.test.ts`. **Ruled out:** not a routing defect (routing
already reads `agree`, `NONE==NONE`, since neither side's truncated head
carries a `data-diagram-type` attribute either); not a genuine unported
feature (this port already refuses the identical inputs, with the
identical ported phrasing `"Syntax Error?"`/`"Empty description"` —
`PSystemBasicFactory.java:96`, `PSystemCommandFactory.java:171` — that the
jar itself emits). **This is a candidate for a follow-on**: widening
`HEAD_BYTES` (or reading until the first `</text>` past the Welcome
boilerplate) in `pin-corpus-tree-measure.ts`/`refusal-coverage.test.ts`
would likely reclassify a chunk of the wider 825-fixture `unknown` bucket
the same way, beyond this cohort — flagged for the orchestrator, not
fixed here (read-only on `src/`, and the measurement script is outside
T6's write-set).

### 2. `PSystemWelcomeFactory`'s genuine tutorial page (2: gujuga, vesuzo)

`vesuzo-97-jelo022` is a literal `@startuml`/`@enduml` with nothing
between: `source.getTotalLineCount() == 2` (`PSystemWelcomeFactory.java:
52`) fires BEFORE any other factory is tried (`PSystemBuilder.java:133`,
first in the array) and returns a real, non-error `PSystemWelcome`
diagram — texts `"Welcome to PlantUML!"`, `"You can start with a simple
UML Diagram like:"`, `"Bob->Alice: Hello"`, ... — no ad, no error marker
anywhere in the full golden (verified). `gujuga-46-vifa350`'s body is a
single PlantUML comment (`'empty`), stripped before the line count, same
result. This port's dispatcher has no analogous "the block is trivially
empty, draw a tutorial" branch; every plugin refuses and `class`'s
refusal (highest-scoring among refusals, `mergeRefusals`) draws the error
sentinel instead. **Ruled out:** not the same mechanism as group 1 — these
two goldens carry zero error markers anywhere, confirmed by a full-file
regex scan, so this is a genuine jar-rendered informational page, not a
truncated error page.

### 3. Recognized single-line utility/easter-egg `PSystemFactory` family
(19: bamudi, fotete, gazale, govuca, jigemu, jivufi, jodesa, kavama,
kenari, kicizi, ludecu, rubeku, tomodo, tukimi, vedine, vofomo, xozane,
xucoma, zusibo)

`PSystemBuilder.java:133-200` registers ~20 single-line "utility"
factories for `@startuml` (`colors`, `sudoku NNNN`, `listfonts [text]`,
`emoji NN`, `openiconic <name>`, `listopeniconic`, `listsprite`, `charlie`,
a curated dedication-phrase list, and a stdlib library catalog) ahead of
the ten legacy UML factories in registration order but gated on
`getDiagramType()`'s "hack" of returning `SEQUENCE` so they're tried for
every `@startuml`. None of this family is ported. Exemplar
`jigemu-90-titu666` (`colors`): `PSystemColorsFactory.java:48`'s
`^colors?\s*(#?\w+)?\s*$` matches the bare line and renders the full named

`class`, `description`, `state` in `src/index.ts` registration order; all

`mergeRefusals` score) draws the error page: our own golden reads
`"Syntax Error? (Assumed diagram type: class)"`. Each of the other 18
fixtures in this group was independently re-measured (full-byte scan for

### 5. `state`'s `/[<>]/` transition pre-filter over-claims (1: kubuju —
**fix-candidate**)

`kubuju-35-neji041`'s body is `listfonts <U+1F680><U+263A><U+1F601>
<U+1F680><U+1F6E0>` (a `PSystemListFontsFactory` fixture, same family as
group 3's font rows — jar golden: `"Fonts available:"`, `data-diagram-type`
absent). This port's `class`, `sequence`, `description` plugins all
correctly refuse it (`classPlugin.parse()` returns `{refused:true, kind:
"syntax", message:"Syntax Error?"}`, verified directly). `statePlugin`,
tried last (`src/index.ts:96-99`), does NOT refuse — `statePlugin.parse()`
returns a fully-formed but EMPTY `StateDiagramAST` (`states:[]`,
`transitions:[]`), which is why `ourType` reads `STATE` instead of the
`NONE` every other member of this cohort gets. Root cause, verified by
direct unit-level calls (`matchAnnotationCommand`/`matchSpriteCommand`
both independently return `null` for this exact line, ruling out the
fallback matchers): `state-commands.ts`'s rule 16 —
```
{ pattern: /[<>]/, passes: ['two'], execute(ps, match) { ... parseTransitionLine(match.input) ... } }
```
(`state-commands.ts:317-319`) — is a deliberately loose "any `<`/`>`
present" pre-filter for transition arrows (`-->`/`<--`/direction-
abbreviated forms), documented in its own comment as relying on
`parseTransitionLine` to reject false positives. But `dispatchCommand`
(`parser.ts:135-144`) treats a PATTERN match alone as "this line is
handled" and returns `true` regardless of whether `execute()` did
anything — so on pass `'one'` the rule matches but is pass-ineligible
(no-op, since `passes:['two']`), and on pass `'two'` `parseTransitionLine`
correctly returns `null` (not a transition) so `execute()` also no-ops —
either way `runPass` never calls `fallbackOrRefuse` (`parser.ts:182-205`)
for this line, and the whole diagram parses "successfully" empty. Upstream
never has this failure mode: `PSystemCommandFactory.java:169-175`'s real
per-command candidate matching only "matches" when a command's FULL
grammar accepts the line; a loose gate that defers real acceptance to
inside `execute()` has no upstream analogue in the ported subsystem.
**Ruled out:** not a `class`/`sequence`/`description` bug (all three
refuse this exact input, verified); not the annotation or sprite fallback
matchers (both verified to return `null` on this line in isolation); not
specific to emoji/Unicode content (`<foo>`, `<<foo>>`, `a <b> c <d>`, and
`<>` alone all reproduce the same silent-swallow, verified).

**D2(b) fix-candidate, D3 landing:** narrowing rule 16 so a matched-but-
inert case (wrong pass with no confirming match, or `parseTransitionLine`
returning `null`) falls through to `fallbackOrRefuse` instead of being
treated as consumed is a small, self-contained change inside
`dispatchCommand`/`state-commands.ts` (est. ≤20 NLOC, no new model) — D2(c)
also clears the bar. After the fix, `state` would join `class` in refusing
this input; with `sequence`/`description`/`class`/`state` all refusing,
`mergeRefusals` picks the highest-scoring refusal (the other 29
`engine=class` rows in this same T6 cohort show `class` consistently
winning that contest for near-identical single-line garbage), so this
fixture would land as `ourType: NONE` via the SAME `class`-refusal error
page as e.g. `jigemu-90-titu666` — i.e. it would move from a ROUTING
`known-misroute` (`STATE` vs jar's `NONE`) into the SAME REFUSAL
`known-gap` bucket as this note's group-3 `PSystemListFontsFactory` rows
(`jivufi`, `jodesa`, `vofomo`) — not a third engine (no stop-5), and a
pure narrowing (D9-compliant: `state` only stops accepting something it
never should have).

## AC5 note (generator behavior vs. the task prompt)

The task prompt states "a fix-candidate row counts as pinned for `--dry`."
Reading `scripts/pin-corpus-tree.ts`'s `computeTally` (`:246-274`) shows
the opposite: `ledgerRow?.disposition === 'fix-candidate'` unconditionally
increments `unpinned`, in BOTH `--dry` and write mode, with no branch on
`opts.dry` anywhere in that function. Verified by running the tool: with
only `T1-settled.json` in the ledger, `--dry` reports `unpinned 157`
(matches the task prompt's own baseline exactly); adding this fragment
(36 rows, 35 `known-gap` + 1 `fix-candidate`) drops it to `unpinned 122` —
a fall of exactly 35, with `kubuju-35-neji041` the one row still counted
as unpinned. So AC5 ("no slug of this cohort may remain unpinned") cannot
be met to the letter while `kubuju` is correctly diagnosed as a
fix-candidate — the brief's own stated exemption for fix-candidate rows
does not exist in the code as written. Keeping `kubuju` classified as
`fix-candidate` (the correct diagnosis, per D2(b)/D3 above) over
mis-classifying it `known-misroute` to force the letter of AC5 follows
`diagnosis.md`: state the mechanism, don't paper over it. 35 of 36 rows
are unconditionally pinned; the 36th is a genuine, small, D2(b)-cleared
fix, one batch-2 task away from `fixed`.
