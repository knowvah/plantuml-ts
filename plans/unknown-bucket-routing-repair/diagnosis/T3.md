### M1 + M2 — classifier declaration: VISIBILITY and TYPE gaps (13: the six
`Class-visibility-N`, `doboco-09-doba683`, `gegosa-79-mini423`,
`girapu-90-pise235`, `jodasa-29-zara935`, `muvici`/`tenule` NOT included here
(see M4), `taboco-79-pire192`, `vijuce-20-xapo285`, `zelura-55-pasa982`)

`class-declaration-parser.ts`'s `DECL_KIND_RE` is this port's single merged
stand-in for TWO upstream `Command`s that share one regex idiom:
`CommandCreateClass` (single-line `class Foo`) and
`CommandCreateClassMultilines` (`class Foo {` … `}`). Both begin with an
*optional* leading visibility character —
`new RegexLeaf(1, "VISIBILITY", "(" + VisibilityModifier.regexForVisibilityCharacter() + ")?")`
(`CommandCreateClassMultilines.java:100`, character class `[-#+~]` at
`VisibilityModifier.java:75-77`) — which `DECL_KIND_RE` has no capture group
for at all: `'^(abstract\\s+class|abstract|class|interface|enum|annotation|
entity|circle|protocol|' + ALL_DESCRIPTIVE_LEAF + ')\\s+(.+)$'`
(`class-declaration-parser.ts:79-81`). Exemplar `Class-visibility-0`:
```
@startuml
+class A {
}
@enduml
```
`class.parse()` refuses at line 1 (0-indexed), `consumed=1`,
`commandScore=0` (`refusalScore` 10) — `DECL_KIND_RE.exec('+class A {')`
returns `null` because the line starts with `+`, not one of the alternated
keywords. `sequence`/`activity` refuse at `consumed=0` (score 0); `state`
also scores 10 but class wins the tie by registration order
(`mergeRefusals`, first-registered wins). All six `Class-visibility-N`
fixtures are the same six-line permutation (brace-vs-bare, with/without a
space after the visibility char) of this one gap. Fixing it (add the
optional `[-#+~]\s*` prefix, thread the captured char into `ClassifierDecl`
or discard it if no render-side field consumes visibility on a classifier
today) is the entire fix; the trailing content in every one of these six
fixtures is otherwise a trivial, already-supported empty class body, so
`class` wins outright once its own refusal disappears — lands `CLASS`
(D3).

The SAME regex's TYPE alternation is separately missing eight of upstream's
keywords: upstream's is `interface|enum|annotation|abstract[%s]+class|
static[%s]+class|abstract|class|entity|protocol|struct|exception|
metaclass|stereotype|dataclass|record` (`CommandCreateClassMultilines.
java:103`; the single-line variant `CommandCreateClass.java:87` additionally
has `circle|diamond|...|map`, both already present or irrelevant to this
cohort). This port's alternation has `abstract\s+class|abstract|class|
interface|enum|annotation|entity|circle|protocol` plus the descriptive-leaf
spread — missing `static\s+class`, `struct`, `exception`, `metaclass`,
`stereotype`, `dataclass`, `record`, `diamond`.

This is a REOPENING of a prior, deliberate decision:
`class-classifier-ast.ts`'s own `'protocol'` doc comment records that
`struct`/`exception`/`metaclass`/`stereotype`/`dataclass`/`record` were
read from the SAME upstream alternation during `dispatch-by-parse-attempt`
(T14) and explicitly NOT ported, because "none is exercised by this
engine's refusal-coverage bucket" and each needs its own badge-glyph
outline (`class-badge.ts#BADGE_GLYPH_D` has no S/X/D/R entry). T3's cohort
is exactly the fixture evidence that premise no longer holds for four of
those six (`metaclass`→girapu, `exception`→jodasa, `struct`→zelura,
`dataclass`→doboco): `class-badge.ts`'s existing "default/unsurveyed kind"
fallback (already used by `protocol`/`entity`/`circle`/`object`) covers the
badge glyph without a bespoke outline, so this is not a NEW gap, it is the
same one T14 already accepted for `protocol`.

Per-fixture:

- `gegosa-79-mini423` / `taboco-79-pire192` (`diamond diamond1` /


### M4 — unicode identifiers in the 6-pre standalone-member shorthand (2: muvici-42-dumo371, tenule-05-fovi294)

```
package 春春春 {
Classe *-- "ει" 春 : τρέχει
春 : 春燕
...
```
`Classe *-- "ει" 春 : τρέχει` (a relationship line, endpoint `春`) parses
fine — the relationship grammar's `CLASS_ID` fragment is already Unicode-
aware. The VERY NEXT line, `春 : 春燕` (upstream's `CommandAddMethod`
shorthand for adding a member to an existing/new classifier without
braces), refuses: `class-command-relationships.ts:54`'s pattern is
`/^("[^"]+"|\.?\w+(?:\.\w+)*)\s*:(?!:)\s*(.+)$/` — JS `\w` is ASCII-only
(`[A-Za-z0-9_]`), so it does not match `春`. Upstream's NAME group for the
identical construct is `([%pLN_.]+|[%g][^%g]+[%g])`
(`CommandAddMethod.java:64`) — `%pL`/`%pN` are PlantUML's Unicode
letter/number regex macros. `class` refuses at `consumed=5` (muvici) /
`consumed=7` (tenule) — the difference is purely leading `'`-comment line
count (1 vs 3), same offending line otherwise. `description` refuses
earlier in both (score 30 vs class's 50/70), so `class` already wins the
merge today; fixing the regex only removes the refusal, it does not change
which engine wins — lands `CLASS` (D3). Estimated size: ~3 NLOC (swap
`\w+` for a Unicode-aware character class with the `u` flag, e.g.
`[\p{L}\p{N}_]+`, reusing whatever fragment the relationship grammar
already uses for the SAME purpose two lines earlier in the same fixture).

### M5 — json-body premature close on an interior bare `}` (1: neticu-06-bafo691)

```
json J {
  "phoneNumbers": [
    { "type": "home", "number": "212 555-1234" },
    { "type": "office", "number": "646 555-4567" }
  ]
}
```
Bisected directly (truncating the fixture line-by-line through
`parseClass`, not inferred from the refusal fields alone): the `json J {`
opener already works — `class-json-commands.ts`'s adapter over the shared
`core/command/CommandCreateJson.ts` port is wired into `COMMANDS` and
creates a `kind: 'json'` classifier correctly. The body closes at
`parser.ts:259`: `if (/^\}\s*$/.test(line)) { closeJsonBodyIfPending(state);
... state.pendingBodyId = null; }` — this fires on the FIRST line that is
just `}`, with no validity check. The JSON value has an interior object
whose OWN closing brace is a bare `}` (the second `{ "type": "office", ...
}` entry, no trailing comma) — that line closes the pending body early;
the array's own `]` and the classifier's real closing `}` are then
dispatched as fresh top-level lines, and nothing recognizes a bare `]` →
refusal (`consumed=11`, `line=11`, counting from `@startuml` as line 0 —
the offending line is `  ]`, the phoneNumbers array closer).

Upstream's `CommandCreateJson` has the textually IDENTICAL naive END regex
— `Pattern2.cmpile("^[%s]*\\}[%s]*$")` (`CommandCreateJson.java:76-77`) —
but `CommandMultilines2#isValid` (`CommandMultilines2.java:105-109`) only
uses a matching END line as a CANDIDATE close: it calls
`finalVerification(lines)`, and `CommandCreateJson#finalVerification`
(`:155-160`) attempts a REAL JSON parse of the accumulated block; on
failure it returns `CommandControl.OK_PARTIAL` (keep collecting), not
`NOT_OK`. So upstream retries the "is this actually the end?" check on
EVERY subsequent bare-`}` candidate until the whole block finally parses
as valid, balanced JSON. This port's `handlePendingBodyLine` has no such
retry — it treats the first candidate as authoritative. `class` still wins
the eventual merge once fixed (it is already the only engine parsing this
far into the fixture) — lands `CLASS` (D3). Fix: in the `kind === 'json'`
branch, on a bare-`}` candidate, tentatively try
`parseJsonNode` (`core/command/CommandCreateJson.ts:256`, already returns
`null` on invalid input, mirroring upstream's `getJsonValue`) over the
joined `pendingJsonLines` + this line; only close the body if it parses,
otherwise push the line and keep going (same as the non-closing branch
already does). Estimated size: ~18 NLOC, reusing the existing parser.

### M6 — description element body closes on a nested `[`/`]` pair (1: rozugu-82-pera583, cross-seam check: NONE, contained to description)

```
rectangle A [
{{
skinparam BackgroundColor #Transparent
rectangle FailCase [
**Fail Case**
----
åäöÅÄÖ
test 1 %newline()This is a newline :-)
test 2
]
}}
]
rectangle OkCase [ ... ]
```
`description` (`consumed=10`, `line=11`, 0-indexed from `@startuml` — the
offending line is `}}`) wins the merge (`class` scores 20, `state` 10).
Bisection of `continueElementBlock` (`src/diagrams/description/
parser.ts:161-176`) against `ELEMENT_MULTILINE_END1_RE = /^([^[\]]*)\]$/`
(`parse-helpers.ts:435` — itself a faithful port of upstream's own
`END1 = "^([^\\[\\]]*)\\]$"`, `CommandCreateElementMultilines.java:83-84`,
so the REGEX is not the gap) shows the element body closes on the FIRST
line ending `]` with no bracket-prefix, which is the interior
`rectangle FailCase [ ... ]`'s OWN closing `]` (`]` alone, line 11 of the
fixture) — not the outer `rectangle A [ ... ]`'s real closer at line 13.
`}}` (line 12) is then dispatched as a fresh top-level line and refuses.

Upstream's PER-LINE end regex is exactly this naive, too — the actual
protection lives one level UP, in the generic multi-line body COLLECTION
loop every `CommandMultilines2` shares:
`PSystemCommandFactory#isMultilineCommandOk` calls
`addOneSingleLineManageEmbedded2` (`PSystemCommandFactory.java:267-303`)
to add each line; when a line matches `EmbeddedDiagram.getEmbeddedType(...)`
(`EmbeddedDiagram.java:257`, the `{{` opener, optionally naming an engine),
it slurps every subsequent line VERBATIM — tracking nested `{{`/`}}` depth
via `EMBEDDED_END = "}}"` (`EmbeddedDiagram.java:78`) — without testing the
END pattern against any of them, resuming normal per-line END testing only
once the embedded region's `}}` is consumed. This port has NO equivalent
anywhere (only place `{{`/`}}` is mentioned in this port's description
engine is a doc comment on `isNoteTerminator` noting the (anchored, exact-
match) note terminator regex is incidentally safe from a FALSE match
inside embedded content — that is not depth-tracking, and does not apply
here since `]`-ending is not anchored to a specific token the way
`end note`/`}` are).

**Scope note**: this is a NARROW guard local to `continueElementBlock`
(add an `embeddedDepth` counter to `PendingElementState`, detect `{{`/`}}`
lines, skip the END test while depth > 0) — not a full port of
`addOneSingleLineManageEmbedded2` for every multi-line command in every
engine, which would be a materially larger, cross-engine change. The
narrow version is sufficient for this fixture (and is self-contained to
description); a fixture nesting `{{ }}` inside a class/state/note body is
NOT covered by this fix and is a separate, currently-unmeasured gap.
Estimated size: ~30 NLOC. See the D3 caveat immediately below for where
this fixture actually lands once the refusal stops.

**D3 caveat, stated plainly**: the jar types this fixture `CLASS`
(`data-diagram-type="CLASS"` in the golden), while this port's own
`description` engine is the one that gets furthest today AND would still
be the one to accept it once M6 lands (nothing about the `{{ }}` fix
changes which of the five candidates wins — `description` already
out-scores `class`/`state` by a wide margin, `consumed=10` vs `2`/`1`).
Fixing M6 does NOT make this fixture land on `CLASS`; it stops the
refusal and lands `DESCRIPTION`, a diagram-type MISMATCH against the jar
that would need `dispatch-by-parse-attempt`-style candidate-set
reconciliation (both `class` and `description` register overlapping
container commands, per the pre-existing `kokebo-27-vafi688` residual
documented in `routing-heuristic-repair`'s closing summary) to actually
resolve. **This row is filed `fix-candidate` for the REFUSAL gate (it
stops erroring, a real defect closes) but will NOT close the ROUTING gate
for this slug** — flagging this explicitly since it is exactly the kind of
distinction D3 asks to be stated, not assumed.

### M7 — Tim `!function` call resolution gap inside the classy stdlib (1: xuloxo-85-vibu502, known-gap)

```
@startuml
!include <classy-c4/container>
!include <classy-c4/person>
!include <classy-c4/system>
... $new/$call OOP-style construction ...
@enduml
```
This include chain pulls in `assets/stdlib/classy/plumbing/
class-instancing.puml`, which defines (among others)
`!unquoted function $isDerivedFrom($class, $ancestorClass)` (line 230) used
by `!unquoted procedure $assertType` (line 175-179,
`!if (%not($isDerivedFrom($determineType($actual), $expected)))`) and,
recursively, by itself inside a `!while` loop (line 257). This port's Tim
expression evaluator throws `Unknown built-in function $isDerivedFrom` at
`src/core/tim/expression/ReversePolishInterpretor.ts:74` (`fn === undefined`
from `knowledge.getFunction(...)`), the direct analog of the lookup-miss
throw at `ReversePolishInterpretor.java:99` (`knowledge.getFunctionSmart`
resolving via `FunctionsSet.java:53`). The jar renders this exact source
successfully (`data-diagram-type="CLASS"`, no jar error page) — a real
port gap, not a routing miss.

**Ruled out** (both via direct, isolated `renderSync` repros against this
port, not upstream reading): (1) plain self-recursion of a `!function` — a
minimal `$fact($n)` calling itself renders correctly (`5! = 120`); (2)
same-file forward reference — a function calling another function defined
LATER in the same file, invoked only after the whole file is processed,
also renders correctly. So the gap is narrower than "recursion" or
"forward reference" in general; it is specific to something in classy's
longer `!unquoted function`/`!while`/nested-call-as-argument chain that
this task did not further isolate — Tim/preprocessor internals are outside
the six seams (`class`/`description`/`state`/`activity`/`sequence`/
`block-extractor`) this mission's `seam` enum covers, so no `seam`/
`command`/`size` is given for this row; a dedicated Tim diagnosis is the
right next step, not a T3 fix.
