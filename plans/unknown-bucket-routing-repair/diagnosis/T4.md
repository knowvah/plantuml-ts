# T4 — class-jar misroutes cohort (46)

`cohorts/T4.tsv`: 46 fixtures the jar renders `data-diagram-type="CLASS"`
that this port routes elsewhere — 42 to DESCRIPTION, 3 to SEQUENCE, 1 to
STATE. Measured against the live tree (`test-results/dot-cache-unknown-2026-09-20`)
through the gates' own seams (`renderSync` + `DeterministicMeasurer` +
`fixtureIncludeStore()`), and, per-line, by calling `classPlugin.parse()`
directly on the same `UmlSource` the dispatcher builds (never by removing a
plugin from the candidate set — that path is forbidden by the brief).

## Mechanism A — missing `CommandCreateElementMultilines` (37)

**Exemplar: `boguko-42-zuda981`.** Source (after `!procedure` expansion):

```
rectangle myalias as "
<color:green><<myalias>></color>
====
//<size:10>[Java]</size>//

This description is on several lines"
```

Our `classPlugin.parse()` dispatches line 0 (`rectangle myalias as "`)
straight to `DESCRIPTIVE_LEAF_COMMANDS` (`class-descriptive-leaf-command.ts:91-128`,
`COMMANDS[44]`, confirmed by direct pattern-table trace, not inferred from a
name) — verified via `state.currentLine`, which reports raw source line
**2** (0-indexed from `@startuml`; matches the jar's own
`data-source-line="2"` on the golden), i.e. line 2 of the raw file: the
`rectangle $alias as "` line *inside* the `!procedure` body. That command
requires either `allowmixing` or `isContainerOpener` (line ends in `{`/`[`);
this line ends in an *open quote*, so neither applies, and it refuses
immediately with `ALLOW_MIXING_ERROR` ("Use 'allowmixing' if you want to mix
classes and other UML elements.") at line 2.

Upstream's `ClassDiagramFactory` does **not** gate this construct at all:
`rectangle CODE as "Display"` (CODE-then-quoted-DISPLAY, the reverse shape of
`CommandCreateElementFull2`'s `TYPE "Display" as CODE`) is exclusively
`CommandCreateElementMultilines.TYPE0`
(`descdiagram/command/CommandCreateElementMultilines.java:96-108`), a
`CommandMultilines2` with `MultilinesStrategy.REMOVE_STARTING_QUOTE` that
consumes lines until one ends in a bare `"` (`END0 = ^(.*)["]$`,
`java:80-81`) and creates a `LeafType.DESCRIPTION` entity with the
`rectangle` USymbol — **unconditionally**, no `isAllowMixing()` check
anywhere in its `executeNow`
(`CommandCreateElementMultilines.java:169-220`). It is registered at
`ClassDiagramFactory.java:166-167`, *after* `CommandCreateElementFull2`
(`:133-134`) — the ordering this port's `class-commands.ts` file otherwise
mirrors rule-by-rule, but this specific rule (rule 9's shared multi-line
sibling) was never added.

The bracket-shaped sibling, TYPE1 (`<kw> <code> [ ... ]`, closing on a line
ending in `]`), is the SAME missing command
(`CommandCreateElementMultilines.java:110-122`, `END1 = ^([^\[\]]*)\]$`).
Re-measured on `buitin-newline-chr-0` (`rectangle A [` /
`test 1\ntest 11` / … / `]`) and `cepedu-19-namu934` (`package foo1 [` /
`text containing \n description of foo` / `]`): here the opening line ends
in `[`, so `isContainerOpener` (CONTAINER_KEYWORD *and* a trailing
`{`/`[`) is true and the `allowmixing` gate does **not** fire; instead
`applyClassifierDecl` treats the line as a bodyless container declaration,
and the very next content line has no matching command at all —
`buildSyntaxRefusal` (`parser.ts:354`) fires there (line 3 for buitin, line
2 for cepedu; positions re-derived via `mergeStandaloneBraces`, not the raw
preprocessed-array index).

Re-measured against every other row in this bucket by re-running the exact
same trace (real `COMMANDS` table, real `mergeStandaloneBraces`, not
synthetic): all 37 share one of these two shapes, including keywords this
port intentionally *excludes* from its own `DESCRIPTIVE_LEAF_KEYWORDS` list
(`entity`, `circle` — `class-descriptive-leaf-keywords.ts:22-27`) because
upstream registers `CommandCreateClass`/`CommandCreateEntityObjectMultilines`
for those FIRST; those two ARE in upstream's shared
`CommandCreateElementFull.ALL_TYPES`
(`descdiagram/command/CommandCreateElementFull.java:76`), so
`CommandCreateElementMultilines` still owns their `[…]` form once the
earlier, brace-only commands decline a trailing `[` (verified:
`felixe-38-dilu011` `circle A […]`, `gogisu-39-bepa573` `entity ABC […]`).
`josebu-55-seje426` needed the real `fixtureIncludeStore()` (an empty store
turns its `!include <cloudinsight/tomcat>` into a hard preprocessor
failure, a probe artifact, not the routing defect) — re-measured with the
real store it renders DESCRIPTION with no error, same TYPE1 `frame FooBar […]`
shape; note its body also contains a `{{ … }}` nested diagram, which trips
an unrelated, already-known limitation
(`EntityImageDescriptionDelegates.ts:124`, "embedded diagrams inside a
description label are not supported") that would likely resurface once it
lands in class — flagged for the batch-2 task, not this diagnosis.

**D3 — where it lands after the fix:** CLASS (matches the jar on all 37;
`classPlugin` is tried before `descriptionPlugin`/`statePlugin`/`sequencePlugin`
in `src/index.ts`, so once class stops refusing, class wins outright — no
narrowing needed on any other engine, and D1's frozen order is untouched).

## Mechanism B — crow's-foot arrow grammar gaps (4)

**Exemplar: `dajela-44-zovi778`** — `Entity01 }|..|| Entity02`, one line,
`REL_DISPATCH_RE.test(...)` returns `false` (measured directly against the
real regex, not inferred). Upstream's `CommandLinkClass` allows `.` (and
`=`) as body characters in BOTH arrow-body groups
(`ARROW_BODY1 = "([-=.]+)"`, `ARROW_BODY2 = "([-=.]*)"`,
`CommandLinkClass.java:133,140`) and registers the crow's-foot decorators
(`}`/`{`, `}o`/`o{`, `|o`/`o|`, `}|`/`|{`) via `LinkDecor.java:80-90`. This
port's crow's-foot alternative in `REL_ARROW`
(`class-relationship-parser.ts:119-131`) reuses the general `DASH` token
(`:66`, `-+(?:${ARROW_DIR}-*)?`) for the body between the crow's-foot ends —
dashes only, no dots — so a dotted crow's-foot body (`..`) never matches.

`fakone-16-boro774` is the same line after a leading `!pragma layout
smetana`; `mujega-45-mexi048` line 1 (`Bob |o--|{ Alice : hello`) DOES
match (dashed body, no style bracket — confirms the crow's-foot alternative
itself is otherwise present and working), but line 2 (`Ted
|o-[thickness=5]-|{ Alice : hello`) does not, because upstream's
`ARROW_STYLE1` bracket sits *inside* a decorated arrow (between body1 and
the direction/INSIDE token, `CommandLinkClass.java:134-136`) and this
port's crow's-foot branch has no such insertion point at all.
`zefefo-37-xigo245`'s failing line (`a 0-[dashed]--0 b: test1`) uses
upstream's separate `INSIDE` "0" cardinality token / `LinkDecor.CIRCLE`
head (`decors1("0")`/`decors2("0")`, `LinkDecor.java:90`), which this
port's `HEAD1_SAFE`/`HEAD2_CHARS` tables (`class-arrow-grammar.ts:102-104`)
never include.

**D3 — where it lands after the fix:** CLASS (matches the jar on all 4;
`REL_DISPATCH_RE` failing to match is the sole blocker — every other line
in each of these four fixtures already parses).

## Mechanism C — `CLASS_ID` ignores `namespaceSeparator` (1)

**Exemplar and only row: `gemepu-46-dido441`** —
`set namespaceSeparator \` then `CustomController --|> App\Http\Controllers\Controller`.
`state.namespaceSeparator` IS threaded to `parseRelationshipLine` for
*splitting* a matched id (`class-command-relationships.ts:82`,
`idLeaf`/`splitOnSeparator`, `class-relationship-parser.ts:363-374`), but
the regex that decides whether the line even LOOKS like a relationship —
`ID_ATOM = [\p{L}\p{N}_$]+`, `CLASS_ID = \.?ID_ATOM(?:\.ID_ATOM)*(?:::ID_ATOM)?|"…"`
(`class-relationship-parser.ts:51-52`) — hardcodes a literal `.` as the
only inter-segment separator and has no backslash (or any configurable
character) in `ID_ATOM`'s class. Upstream's own endpoint grammar is
generic, not templated from the configured value: `getSeparator()` =
`SEPARATOR_CHAR_SINGLE` (`[^%pLN%s_$#\:{}<>%g]`, *any* single
non-identifier/non-punctuation-reserved character) OR
`SEPARATOR_CHAR_DOUBLE` (`\\{2}|::`) (`CommandLinkClass.java:87-95`) — so
upstream accepts whatever separator character the source actually uses.
`App\Http\Controllers\Controller` never matches this port's `CLASS_ID`/
`REL_DISPATCH_RE` regardless of what `nsSep` is configured to, so
`dispatchCommand` finds nothing and `buildSyntaxRefusal` fires on the
relationship line (raw line 2).

**D3 — where it lands after the fix:** CLASS (matches the jar; this is the
only failing line in the fixture).

## Mechanism D — dotted note name (1)

**Exemplar and only row: `rexupa-61-nezi165`** —
```
note as n
    my note
end note

note as X.n
    my enother note
end note
```
The first `note as n` parses fine. The second, `note as X.n`, fails:
`state.currentLine` at refusal is **5** (0-indexed from `@startuml`) — the
`note as X.n` line itself, not its body. Upstream's `CommandFactoryNote`
allows a dot in the note's own name
(`CODE = "([%pLN_.]+)"`, `command/note/CommandFactoryNote.java:83,101` — a
namespaced note id is ordinary upstream syntax). This port's two
note-declaration patterns
(`class-command-notes.ts:124,151`) use `(\w+|"[^"]+")` for the same
capture — `\w` excludes `.` — so `note as X.n` matches neither and the line
itself, not a body line, is where dispatch fails.

**D3 — where it lands after the fix:** CLASS (matches the jar; the rest of
the fixture, including the first `note as n` block, already parses
correctly).

## Mechanism E — sequence over-claims (3)

**Exemplar: `jamupa-36-duni483`** — `a -[thickness=5]> b`. Our
`registry.resolve()` (real registry, all plugins registered via `src/index.ts`,
not a synthetic candidate set) picks `sequence` for this source; separately,
`classPlugin.parse()` on the same `UmlSource` returns a full AST (no
refusal) — class WOULD claim it if sequence got out of the way. Bisected
against the real jar (`scripts/oracle-render.sh`, three single-probe
renders): `a --> b` → `SEQUENCE`; `a -[dashed]-> b` → `SEQUENCE`;
`a -[thickness=5]-> b` → `CLASS`. The `thickness=` token is the trigger, not
the bracket syntax itself.

Root: upstream's sequence `CommandArrow.applyStyle`
(`sequencediagram/command/CommandArrow.java:482-502`) tokenizes the style
bracket and recognizes only `dashed`/`bold`/`dotted`/`hidden` by name;
**everything else** — including `thickness=N`, which the SHARED
`CommandLinkElement.LINE_STYLE` regex used to build the arrow pattern
happily matches syntactically (it is valid style vocabulary for a
class-diagram *link*, `CommandLinkElement.java:71`) — falls to
`HColorSet.instance().getColor(s)` and throws `NoSuchColorException`. That
checked exception propagates as a `Throwable` out of
`factory.createSystem(...)`; `PSystemBuilder.java:256-271`'s per-factory
loop catches `Throwable`, records a "fatal crash" error for that factory,
and moves on to the next candidate (class), which correctly parses the
same line as a class relationship. This port's `command-arrow.ts` has no
equivalent style-token whitelist — it accepts `thickness=N` as valid
sequence-arrow style — so sequence wins outright.

**Exemplar 2 (same mechanism family, different guard):
`kevegu-65-zagi834`/`lakivi-73-vuko958`** — `Reporter -- Queue` (repeated,
plain double-dash association lines, no style bracket at all). Upstream's
`CommandArrow.executeArg` (`java:298-313`) computes `reverseDefine` by a
cascade over which directional/cross/circle characters (`<`, `\`, `/`, `>`,
`x`, `o`) appear in `ARROW_DRESSING1`/`ARROW_DRESSING2`; when **neither**
dressing carries any of them (a bare `--` body with zero head decoration),
none of the cascade's `if`/`else if` branches fire and the final `else`
returns `CommandExecutionResult.error("Illegal sequence arrow")` — a
normal (non-thrown) refusal this time, but the same "factory declines, try
next" outcome via `PSystemBuilder`'s `isOk(sys)` check. This port's arrow
matcher (`UNDRESSED_ARROW_RE`) has no equivalent "both dressings empty"
refusal, so it accepts a bare association dash as a valid message.

**D3 — where it lands after the fix:** CLASS on all 3 (already measured:
`classPlugin.parse()` succeeds on each of these three sources today; the
fix only needs sequence to stop claiming them, D1's frozen registration
order does the rest).

## Cross-seam (stop 8) check

None of the five mechanisms needs two seams at once. A fixed
`CommandCreateElementMultilines` (class) does not require description to
refuse anything — description's own copy is untouched and unrelated (a
class-engine fixture reaching description today is a routing symptom of
class's refusal, not a description over-claim: `descriptionPlugin` is a
correct, unconditional fallback candidate, exactly as upstream's
`DescriptionDiagramFactory` is). Mechanism E is entirely a sequence-seam
change (narrowing `CommandArrow`); it does not require class to change at
all — class already accepts these three sources. No `cross-seam` rows.
