| 2026-08-13 | **MISSION REOPENED AND CLOSED THE OTHER WAY. Both grounds for the 2026-08-08 ruling were false; `bipudo-23-xavu432` is re-pinned at 0 diffs (312 → 313).** (1) The premise "just over the 0.01 tolerance" was never true — `0.0097` is *inside* the band. Two artifacts stacked: 3-decimal emission rounds `75.1940275463084` and `75.1843` apart to exactly `0.010`, and the comparator's `Math.abs(a-b) > tolerance` then rejected that, because IEEE-754 yields `0.010000000000005116` for the subtraction. The strict `>` is written to ACCEPT an exactly-at-band difference, so this was a harness defect, not a divergence. Fixed as `compare.ts#exceedsTolerance` (slack = 1 ULP scaled to operand magnitude, ~1.7e-14 here); a 1e-4 overshoot still fails, and both directions are pinned by tests confirmed to fail against the naive form. (2) The cause was misattributed to Smetana. This fixture has a `svek-1.dot` and Smetana paths emit none: `svek/DotStringFactory.java:316` calls `create(skinParam, dotString, "svg")` and `GraphvizRuntimeEnvironment#create` dispatches to `GraphvizLinux`, the external binary, whose SVG PlantUML scrapes. `dot -Tsvg` prints 2 decimals — run on this fixture's own DOT it emits `M24.58,-107.74C24.58,...`, reproducing every jar value including the `24.58` T1 could not place. | The 2026-08-08 ruling's reasoning was "we don't chase a graphviz 2.38 transpile", which does not apply to a fixture that never used the transpile. Because both engines agree at full precision and differ only in what `-Tsvg` can print, this is a **serialization-precision** limit that will NOT resolve when the jar updates graphviz — the opposite of the vintage story. T1's "no fix, blanket 2dp breaks eight things" finding still stands and is re-confirmed: quantizing our points to 2dp across 802 class+object fixtures moves only 3, by 1–2 diffs, and flips none to zero. The fix was never quantization; it was the comparator. | no — decided |
