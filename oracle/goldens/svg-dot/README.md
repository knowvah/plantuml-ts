# `svg-dot` — SVG-conformance goldens for `@startdot`

Mission **D14** (dot passthrough). Sibling of `svg-description`, `svg-class`,
`svg-object`, `svg-state`, `svg-skin`.

## Current state

**5/5 conformant, zero diffs.** Every cached `@startdot` fixture is pinned.
That is the whole corpus: pdiff carries two `@startdot` fixtures
(`bemepi-16-kuzo249`, `ciditi-21-xacu710`) and this repo authored three more
(`chain-expansion`, `cluster-basic`, `cluster-nested`).

Baseline before the mission was **0/5**, at ≥6 diffs each — and that count was
an undercount, because the root `svg[childCount]` diverged (2 vs 1) and
`compare.ts` stops recursing on a structural mismatch, so no fixture's interior
was ever compared.

## Why this type is different from its siblings

`@startdot` is a **passthrough**, not a rendering pipeline.

`@see .../directdot/PSystemDot.java#exportDiagramNow` — upstream hands the
accumulated DOT text to the graphviz executable and writes graphviz's own bytes
straight to the output stream. No `TextBlock`, no klimt shapes, no skin. This
port does the same through `@knowvah/dot-engine`'s `renderSvg`. Three
consequences for this directory:

1. **No `render-fixture-dot.ts`.** The other suites use a low-level per-type
   pipeline to keep production defaults (theme, measurer) out of the
   comparison. Here there is nothing to keep out: the passthrough consults
   neither, so the ratchet calls the real `renderSync` — the shortest path that
   is still the shipped one.
2. **No `parity-dot.json`, and no AC3.** The sibling suites gate ratchet
   eligibility on a fixture already being DOT-equal, so a residual SVG diff is
   attributable to SVG assembly rather than layout. For `@startdot` the "DOT"
   is the user's own source, forwarded verbatim — equality is true by
   construction, and a gate asserting it would assert nothing.
3. **The measurer is load-bearing in a way it is not elsewhere.** This path
   lets the engine measure every node label itself. Measured against the jar:
   the engine's default (`EstimateTextMeasurer`) gives 8/5/4/36/33 diffs;
   `LutTextMeasurer` gives 0/0/0/0/0. `src/core/dot-engine-measurer.ts` pins
   it.

## Oracle-stability caveat — read before re-capturing

These goldens are **machine-dependent in a way no other suite's are.** The jar
does not lay `@startdot` out itself; it shells out to whatever graphviz binary
is installed. Every golden here was produced by **graphviz 15.1.0**, recorded
in each file's own `<!-- Generated by graphviz version … -->` comment.

A machine with a different graphviz will produce different goldens, and the
diffs will look like port regressions when they are not. Before concluding that
a failure here is ours, check that comment against the local `dot -V`.

## Add rule

A fixture ratchets in when it renders zero-diff against its `golden.svg` under
`compareSvg(…, 'deterministic')`. Add its directory (`in.puml` + `golden.svg`)
and a `ratchet.json` row. Shrink-only: a pinned fixture never comes back out.

Re-capture with the pinned oracle jar:

```sh
java -DPLANTUML_DETERMINISTIC_TEXT=true -jar oracle/dist/plantuml-oracle.jar \
  -tsvg -o <outdir> <fixture>.puml
```

`-DPLANTUML_DUMP_DOT` is pointless here — see `docs/svg-conformance.md`; the
jar emits no `svek-N.dot` for a passthrough diagram because it never builds one.
